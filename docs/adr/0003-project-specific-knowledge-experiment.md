# ADR-0003 — 3차 실험: 모델이 모르는 프로젝트 고유 지식

- 상태: 채택 (2026-10-09)
- 선행: ADR-0001(1차, 차이 없음), ADR-0002(2차 + 추가 실험 F·Haiku·P-lite)

## 맥락

1·2차와 추가 실험이 확인한 것:

- 카드 내용이 **일반 CS 원리**면 모델이 이미 알고 있다. 카드는 오버헤드다.
  - 카드 전문(P): ÷B 1.35(Sonnet), 1.49(Haiku)
  - 아카이브 우선(F): ÷B 1.87, 1.76
- 이상적 검색+요약(P-lite, L)도 손익분기(÷B 1.12, 1.05)에 그친다. 이득은 정답률(B 실패 3 → 0)뿐이다.
- 유일한 토큰 절감 신호는 모델이 모르는 사건이었다(2차 10번, iconv 부분 변환 — L÷B 0.58).

남은 질문: **원인이 모델의 사전 지식으로 추론되지 않는 정보일 때도 아카이브가 손해인가?** 실무 이슈 아카이브의 진짜 가치는 이쪽(우리 시스템·벤더·운영 고유 사정)일 것이다. MCP(검색+요약) 구축 여부도 이 답에 달려 있다.

## 결정

### D1. 지식 원천 — 가상 사내 시스템 + 블랙박스 외부 의존

- 가상 회사의 업무 시스템 케이스를 만든다. 원인은 사용자 코드가 **벤더 CLI·모의 외부 서비스(블랙박스)의 문서화되지 않은 동작**을 잘못 다루는 데 있다.
- 고칠 곳은 사용자 코드다. 블랙박스는 고치지 않는다.
- 블랙박스 동작은 **일반 원리로 추론되지 않는 임의 규칙**이어야 한다. 예: 특정 필드가 40바이트를 넘으면 오류 없이 보류 처리된다. 특정 플래그가 붙은 출력은 전 영업일 값이다.

### D2. 블랙박스 형태 — 네이티브 바이너리

- C로 작성해 `gcc -O2 -s`(strip)로 빌드한다. 케이스에는 바이너리만 두고(`vendor/bin/`), 소스와 빌드 스크립트는 `oracle-v3/NN/blackbox/`에 둔다.
- 오류는 불투명 코드(`E17` 등)로만 낸다. 규칙을 드러내는 문자열(`memo too long` 등)은 바이너리에 넣지 않는다. `--help`는 있되 해당 동작은 적지 않는다(실제 벤더 문서처럼).
- 결정적으로 동작한다(시각·난수 의존 금지, 필요하면 환경변수로 고정).

### D3. 발견 가능성 — B도 비싸게나마 풀 수 있어야 한다

B가 원리적으로 못 푸는 케이스는 토큰 비교가 아니라 정답률 비교만 된다. 블랙박스 동작은 **실행·탐침(입력을 바꿔 가며 호출)으로 알아낼 수 있어야** 한다. 케이스 작성자는 탐침만으로 규칙을 알아내는 경로가 있음을 확인하고 그 경로를 기록한다(명령 ≤ 10개 수준).

### D4. 케이스 요건

- 2차 v2 요건을 승계한다(`docs/plans/2026-10-08/experiment-v2/worker-brief-v2.md`): 계층 분리, 원인·증상의 층 분리, 미끼 2개 이상, E2E 재현 테스트, 운영 문의형 TASK.md, hidden이 땜질·미끼 수정을 차단.
- 규모는 15~30파일·500~1,500줄로 완화한다. 이번 변수는 "모르는 지식"이지 규모가 아니다.
- 추가 요건: 사용자 코드에 블랙박스 호출부가 있어야 하고, 증상은 그 결과를 쓰는 끝단에서 보여야 한다. 블랙박스를 우회하는 재구현(바이너리 대신 직접 계산)은 hidden에서 실패해야 한다.

### D5. 아카이브 — 가상 회사 전용, study-note와 분리

- 위치: `archive-v3/issue/` (compare-issue-archive 안 — study-note 무변경). 실행 시 `/tmp/cia-lib3/issue`로 복사한다.
- 카드 형식은 study-note와 같은 3파일(1-question / 2-summary / 3-answer)로 한다. 2차와 형식 변수를 같게 하기 위해서다. L용 요약은 `oracle-v3/NN/summary.txt`(카드 결론 2~3줄)에 둔다.
- 구성: 관련 카드 10 + 미끼 카드 10~20(같은 회사의 다른 벤더·시스템 사건). 인덱스 README는 **증상 → 카드 1줄 경량 표**로 한다.
  - 2차 F의 비용 대부분이 65KB 인덱스였다. 이번 아카이브는 새로 만드는 것이라 경량 인덱스를 기본으로 둔다.
  - 따라서 3차 F는 2차 F와 인덱스 조건이 달라 직접 비교하지 않는다(기록).

### D6. arm

| arm | 프롬프트 추가분 |
|---|---|
| B | 없음 (아카이브 접근 금지·감사) |
| L | 정답 카드 결론 요약 2~3줄 (아카이브 접근 금지·감사) |
| P | 정답 카드 경로 + "먼저 읽어라" |
| F | 아카이브 경로 + "먼저 찾아 읽고, 없으면 직접 조사" (2차 F와 같은 문구) |

### D7. 파일럿 게이트 → 본 실험

- 파일럿: 3케이스(Java·Python·TS 각 1)에 대해 B·L 각 1회(Sonnet).
- 통과 기준: L 성공, 그리고 B 실패 또는 B 총 토큰 ≥ L × 1.5. 미달하면 재설계 1회, 그래도 미달이면 사용자 결정.
- 본 실험: 10케이스 × B·L·P·F × 3회 × Sonnet·Haiku = 240회. 나머지 7케이스와 미끼 카드는 파일럿 통과 후 만든다.

## 예측과 판정

- 아카이브 가치가 실재한다면: L÷B ≪ 1(예: ≤ 0.7)이고, P·F도 B보다 싸거나 정답률이 높다. 이 경우 MCP(검색+요약) 구축 근거가 된다.
- L÷B ≈ 1이면: 모르는 지식이어도 탐침 비용이 카드 비용과 비슷하다는 뜻이다. 그러면 아카이브는 토큰이 아니라 정답률·시간 수단으로만 정당화된다.

## 대안 (기각)

- 코드에 없는 사내 규약(정답이 코드에서 유도 불가): B가 거의 못 풀어 토큰 비교가 성립하지 않는다(D3).
- 사용자 실제 프로젝트 사건: 일반 원리로 풀리는 사건이 섞여 변수가 오염된다.
- 언어별 컴파일 산출물(.class·.pyc·난독화 JS): 디컴파일이 쉬워 "모르는 지식" 조건이 약하다.
