# ADR-0001: 1차 실험 — 요구사항과 차이가 안 나온 원인

- 상태: 확정 (2026-10-08)
- 관련: `docs/plans/2026-10-08/case-build/`, `docs/plans/2026-10-08/token-experiment/`, `results/summary.md`, `results/analysis.md`

## 맥락 — 1차 요구사항

사용자 질문: **"issue 문서를 아카이브하는 게 문제 해결에 얼마나 도움이 되나?"** — 같은 버그를

- **A**: issue 아카이브(`study-note/issue/`, 카드 161개)를 참고할 수 있는 에이전트
- **B**: 아카이브 없이 스스로 조사하는 에이전트

에게 맡기고 **토큰 사용량**을 비교한다.

합의된 조건:

| 항목 | 결정 |
|---|---|
| 케이스 | 카드 10개(Java 3·Python 3·TS 3·Shell 1)의 실제 사건을 재현한 코드. 공개본 `cases/`(TASK.md·버그 코드·재현 테스트) / 비공개 `oracle/`(fix.patch·hidden 판정 테스트) |
| 실행 | `claude -p` 헤드리스, 격리 HOME(하네스·훅·메모리·MCP 없음 — "하네스가 아니라 이슈 문서의 효과만"), Sonnet, 실행당 상한 $2 |
| A의 아카이브 사용 | 스스로 찾기(README 인덱스 경로만 안내, "활용해도 된다") |
| 접근 제어 | B는 아카이브 차단 — deny 규칙 + 실행 로그 감사(bwrap은 AppArmor 제한으로 불가) |
| 반복 | 케이스 × arm × 3회 = 60회 |
| 판정 | 재현 test.sh + hidden.sh 통과, 테스트 변조 없음 |

## 결과

60/60 유효·성공. 총 토큰 중앙값 A 89,204 / B 88,020, 비용 합 $2.39 / $2.40. 케이스별 A÷B 0.98~1.06(10번만 0.80). **차이 없음.**

## 원인 분석 — 실험이 "아카이브가 필요한 상황"을 만들지 못했다

| # | 원인 | 근거 |
|---|---|---|
| 1 | **아카이브를 쓰지 않았다** | A 30회 중 10회가 첫 명령에 `README.md | head -50`을 끼웠을 뿐, 카드를 연 실행 0회. A는 사실상 B와 같은 실험이 됐다 |
| 2 | **케이스가 너무 작다** | 10케이스 소스·테스트 합계 987줄(케이스당 ~100줄). 첫 Bash 한 번(`cat TASK.md; ls; cat test.sh` → `cat src/*`)으로 전부 보인다. 탐색 비용 ≈ 0 이라 아카이브로 절약할 것이 없다 |
| 3 | **잘 알려진 함정이다** | 인자 평가 순서·`"" in s`·`return` without `await`·`=== NaN`·반열린 구간 등은 모델 사전 지식에 이미 있다. 카드의 정보가 모델에게 새롭지 않다 |
| 4 | **재현 테스트가 위치를 짚어 준다** | 실패 메시지와 테스트 이름이 증상 지점을 바로 가리키고, 코드가 작아 원인 지점과 붙어 있다 |
| 5 | **천장 효과** | 두 arm 모두 100% 성공, 도구 호출 3~4회. 개선 여지(headroom)가 없으면 어떤 도움도 측정되지 않는다 |
| 6 | **지표가 고정비에 묻힌다** | 호출마다 시스템 프롬프트·도구 정의 ~16k 토큰(첫 호출 컨텍스트 중앙값 16,393)을 다시 읽는다. 4~5턴이면 총 ~88k 중 ~65~80k가 고정비, 캐시 읽기 비중 84.3%. 과제 고유의 변동분이 작아 차이가 희석된다 |
| 7 | **A의 안내가 선택적이다** | "활용해도 된다"만으로는 쉬운 문제에서 열람 동기가 없다. "찾는 행동"과 "카드 내용의 가치"가 한 변수에 섞여 분리되지 않는다 |

## 결정

1차 결과를 **"아카이브는 효과가 없다"로 해석하지 않는다.** 측정 조건의 한계(위 1~7)로 귀속하고, 2차 실험은 ADR-0002에서 이 원인들을 하나씩 제거하도록 설계한다.

## 유지할 것 (1차에서 검증된 장치)

- 격리 HOME `claude -p` — 하네스 없이 정확한 usage를 얻는다.
- deny 규칙 + 로그 감사 — 스모크로 fail-open 아님을 확인했다.
- OAuth 토큰 회전 가드(만료 ≥45분 대기, 갱신본 되쓰기).
- hidden 판정 + 변조 검사, 무효 행도 남기는 기록 방식.

## 추가 실험 — arm F (archive-first) (2026-10-08 append)

> 사용자 질문: "우선적으로 이슈에서 찾아보고 없으면 검색하도록 하는건? 그래도 안 연 거야?" — 1차 A는 "활용해도 된다"(선택)였고, 순서를 강제한 조건은 측정하지 않았다(원인 7). 같은 1차 케이스로 보충했다.

**조건**: 프롬프트 = 1차 공통 + "코드를 고치기 전에 **먼저 이 아카이브에서 관련 카드를 찾아 읽어라.** 관련 카드가 없거나 맞지 않을 때만 직접 조사하라." 나머지 조건(격리 HOME·Sonnet·$2·deny+감사·판정)은 1차와 동일. 10케이스 × 3회 = 30회.

**결과** (유효 30/30, 성공 30/30. 감사 오탐 무효 3건은 행을 보존하고 재실행 — 아래 참고)

| arm | 성공 | 총 토큰 중앙값 | 비용 합 $ | 비용 중앙값 $ |
|---|---|---|---|---|
| B (직접 조사) | 30/30 | 88,020 | 2.40 | 0.077 |
| A (스스로 찾기) | 30/30 | 89,204 | 2.39 | 0.080 |
| **F (아카이브 우선)** | 30/30 | **153,163** | **3.80** | **0.113** |

- 케이스별 F÷B 총 토큰은 1.35~2.11로, **10개 케이스 전부 F가 더 썼다.** 비용은 +58%, 턴 중앙값은 4→6.
- **카드 발견률**: 정답 카드를 연 실행 10/30, 엉뚱한 카드만 연 실행 3/30, 카드를 안 연 실행 17/30. 이 17회는 README만 읽고 관련 카드가 없다고 판단했다.
- **정답 카드를 열어도 줄지 않았다**: F÷B 중앙값은 정답 카드 열람 1.70, 엉뚱한 카드만 1.71, 안 엶 1.49였다.

**원인**

1. **인덱스가 무겁다.** `issue/README.md`는 499줄·65.8KB, 약 2만 토큰이다. F 30회 중 30회가 이것을 통째로 `cat`했다(grep으로 일부만 본 경우 소수). 한 번 읽은 내용은 이후 매 턴 컨텍스트에 남아 다시 읽히므로, 턴 수만큼 곱해져 +4만~9만 토큰이 된다.
2. **인덱스로 카드를 찾기 어렵다.** 인덱스는 "원리" 단위로 분류돼 있고, 에이전트는 "증상"을 들고 온다. 그래서 정답 카드 적중이 1/3에 그쳤다. 예: 08(자동 저장)은 debounce 카드 대신 동시성·키 정규화 카드를 열었다.
3. **쉬운 문제에서는 카드가 줄여 줄 것이 없다**(1차 원인 2·3 그대로). 정답 카드를 읽어도 어차피 4턴이면 풀리는 문제에 카드 읽는 비용만 더해졌다.

**결론**: 지금 형태의 아카이브를 "먼저 보라" 정책으로 붙이면, **쉬운 문제에서는 토큰이 약 1.7배로 늘고 성공률 이득은 없다.** 이 결과는 아카이브의 *내용* 가치가 아니라 *접근 비용*(무거운 인덱스, 증상→카드 매핑 부재)을 보여 준다. 내용 가치는 어려운 케이스에서 재야 한다(ADR-0002).

**감사 오탐 기록**: 03 r1·05 r2·10 r2가 무효였다. Claude Code 권한 가드의 거부 메시지가 deny 규칙 문자열(`//home/jun/project/**`)을 인용해 감사 패턴에 걸렸을 뿐, 실제 접근은 아니었다. `audit()`에서 가드 메시지 안의 규칙 문자열을 마스킹하고(실제 접근은 계속 검출 — 단위 확인), 3건을 재실행했다. 무효 행은 `runs.jsonl`에 남겨 두었다.
