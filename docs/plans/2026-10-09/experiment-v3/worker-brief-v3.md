# 케이스 v3 작성 워커 공통 브리핑

## 목표

1·2차 실험 결과, 카드 내용이 **일반 CS 원리**면 모델이 이미 알고 있어서 이슈 아카이브는 토큰 손해였다. 3차는 **모델이 사전 지식으로 알 수 없는 프로젝트 고유 지식**에서 아카이브 가치를 잰다. 필독 순서:
1. `docs/adr/0003-project-specific-knowledge-experiment.md` (D1~D5)
2. `docs/plans/2026-10-08/experiment-v2/worker-brief-v2.md` (v2 요건 — 이 브리핑이 다르게 정한 것 외에는 승계)
3. 1차 브리핑 `docs/plans/2026-10-08/case-build/worker-brief.md` (폴더 계약)
4. 참고 예시 `cases-v2/10-partner-settlement/`, `oracle-v2/10-partner-settlement/` (구조만 참고, 수정 금지)

실험에서는 Sonnet·Haiku 에이전트가 이 케이스를 4가지 조건으로 고친다. B는 증상만, L은 카드 결론 요약 2~3줄, P는 카드 전문, F는 아카이브 검색이다. 이 조건들의 토큰을 비교한다.

## 만들 것 (워커 1명 = 케이스 1개)

1. `cases-v3/NN-name/` — 가상 회사 "한빛페이"의 업무 시스템 코드다. TASK.md·test.sh·소스·테스트, 그리고 **`vendor/bin/<도구>` 바이너리(strip 빌드 산출물)**를 둔다.
2. `oracle-v3/NN-name/`
   - `card.txt`: 첫 줄 `issue/<카드경로>` + 채택 근거.
   - `fix.patch`
   - `hidden/hidden.sh` + 필요한 hidden 테스트
   - `blackbox/` — 바이너리 C 소스와 `build.sh`(`gcc -O2 -s -o ...`). 빌드 결과는 케이스의 `vendor/bin/`에 넣는다.
   - `summary.txt`: 카드 결론 2~3줄. 케이스 코드의 파일명·함수명·변수명은 쓰지 않는다.
   - `probe.md`: 탐침 경로. B가 바이너리를 실행만 해서 규칙을 알아내는 명령 ≤10개와 각 출력.
3. `archive-v3/issue/<시스템>/<slug>/` 카드 3파일: `1-question.md`·`2-summary.md`·`3-answer.md` + `metadata.md`.
   - 형식은 `/tmp/cia-lib/issue/authoring-guide.md`와 기존 카드 1개(예: `/tmp/cia-lib/issue/shell/exit-status-semantics/`)를 읽고 따른다(읽기 전용 사본).
   - **카드의 사건은 같은 블랙박스 규칙을 다른 서비스·다른 증상에서 겪은 과거 사건**으로 쓴다. 현실의 사내 아카이브처럼, 이번 케이스와 똑같은 사건이 아니라 같은 원인의 이전 사건이다.
   - 카드만 읽으면 규칙(무엇을 하면 어떻게 동작하는지)과 올바른 대처를 알 수 있어야 한다.

## 블랙박스 요건 (ADR D1~D3)

- **임의 규칙**: 일반 CS 원리나 공개 표준으로 추론되지 않는, 이 벤더 고유의 문서화되지 않은 동작이어야 한다. 오류 없이(exit 0) 조용히 다르게 동작하는 쪽이 좋다.
- **불투명**: 오류는 `E17` 같은 코드로만 낸다. 규칙을 드러내는 문자열은 바이너리에 넣지 않는다(`strings vendor/bin/x | grep -i <규칙 관련 단어>` 0건). `--help`는 사용법만 적고 해당 동작은 적지 않는다.
- **결정적**: 시각·난수 의존을 금지한다. 상태가 필요하면 케이스 폴더 안 파일(환경변수로 경로 지정)에 둔다.
- **발견 가능**: 바이너리를 다른 입력으로 실행해 보면 규칙을 알아낼 수 있어야 한다(probe.md에 기록, 명령 ≤10개). 다만 코드만 읽어서는 알 수 없어야 한다.
- 고칠 곳은 사용자 코드다(호출부·전처리·결과 해석). 바이너리는 고치지 않는다.

## 케이스 요건

- v2 요건 승계: 계층 분리, 원인과 증상이 다른 층, 미끼 2개 이상, E2E 재현 테스트, 운영 문의형 TASK.md(원인 힌트·벤더 동작 언급 금지), 통과하는 노이즈 테스트.

## 추가 요건 — 파일럿 교훈 (2026-10-09, 04~10 케이스용)

파일럿 결과(B÷L): 01 환율 1.12 → 재설계 후 1.40(미달), 02 원장 1.78, 03 발행 2.03(통과).
- **01이 싼 이유**:
  - 옵션·입력 공간을 bash 루프 한 번으로 전수 조회할 수 있었다(`for s in 0 1 2 3; for d in ...`).
  - 첫 설계에서는 옵션 이름(`--fix`)이 답을 말해 줬다.
- **02·03이 비싼 이유**: 조용한 유실이었다. exit 0이고 접수 응답도 정상이라, 저장된 상태를 다른 명령(list·show·stat·consume)으로 확인해 봐야 드러났다. B는 9~10회 호출했다.
- 따라서 04~10은 **02·03형**으로 만든다.
  - 블랙박스가 오류 없이 정상 응답하지만 결과 상태가 조용히 다르다.
  - 그 사실은 다른 조회 명령으로 상태를 들여다봐야 보인다.
  - 옵션 이름·도움말·바이너리 문자열이 규칙이나 대처를 말해 주지 않는다.
- 카드 경로는 `archive-v3/issue/<도구명>/<slug>/`로 한다(예: `issue/ledgerctl/memo-byte-silent-hold`).
- 같은 회사의 다른 케이스가 이미 쓴 규칙 유형(바이트 길이 상한·키 접두 dedupe·휴장일 이월)과 겹치지 않게 한다.
