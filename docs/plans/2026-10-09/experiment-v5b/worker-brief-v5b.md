# 5차-b 케이스 작성 워커 공통 브리핑 (의사결정 히스토리)

## 목표

1~4차는 **버그 고치기**에서 이슈 기록의 가치를 쟀다. 결론은 "모델이 모르는 벤더 고유 동작을 적은 카드는 토큰을 절반 안팎으로 줄인다"였다.

5차-b는 다른 질문을 잰다. **"왜 이렇게 정했나"라는 회사 고유의 의사결정 기록이, 변경 요청을 구현하는 에이전트가 과거 결정을 깨지 않게 하는가?**

필독:
1. `docs/adr/0006-decision-history-experiment.md`(확정 절 포함)

3. 3차 브리핑 `docs/plans/2026-10-09/experiment-v3/worker-brief-v3.md`: 폴더 계약·누출 금지·보고 형식을 승계한다. 블랙박스 요건은 이번엔 해당하지 않는다.
4. 담당 케이스의 `cases-v6/NN-*/` 전체와 `oracle-v4/NN-*/card.txt`(코드 구조 파악용)

   - `archive-v3/issue/README.md`
   - `archive-v3/issue/ledgerctl/memo-byte-silent-hold/` 4파일

실험에서는 Sonnet·Haiku 에이전트가 이 케이스의 변경 요청을 네 가지 조건으로 구현한다.

## 만들 것 (워커 1명 = 케이스 2개 + 미끼 기록)

### 1. 과거 결정 하나를 정하고 코드에 그 결과를 심는다 (`cases-v6/NN-*/`)

- 결정은 이 서비스의 동작 규칙이다. 결정 유형은 아래 "배정"을 따른다.
  - 예(환불): "부분 환불은 즉시 PG에 보내지 않고 D+1 06:00 배치로 모아 보낸다"
- **이유는 회사 고유 사정이어야 한다.** 일반 모범 사례·공개 표준·상식으로 유도되면 안 된다.
  - 예: "PG 계약 부속서 7조가 같은 승인번호의 당일 부분 취소를 원 결제 취소로 처리해서, 2024-03에 고객 이중 환불 사고가 났다"
  - "멱등성이 좋으니까" 같은 일반 원리는 금지다(ADR-0002: 모델이 이미 아는 지식은 기록 가치가 없다).
- 코드에는 결정의 **결과만** 남긴다(구조·상수·분기). 이유를 한 곳에 직접 적지 않는다.
- 결정 결과가 "요즘 보기엔 불필요하거나 과해 보이는" 모양이면 더 좋다. `TODO: 이거 아직 필요한가?` 같은 오해를 부르는 미끼 주석 1개를 허용한다.

### 2. 단서를 파일 2~4곳에 흩어 둔다 (git 이력 없음)

- 후보: 코드 주석 조각, 테스트 이름이나 테스트 안 픽스처 주석, 운영 스크립트·런북, `CHANGELOG`, `docs/` 메모, conf 주석
- 각 단서는 조각이어야 한다. 하나만으로는 결정의 이유를 다 알 수 없고, 2~3개를 이어야 복원된다.
- `DO NOT CHANGE because …`처럼 한 줄로 다 말하는 주석은 금지다.
- B가 단서로 결정을 복원하는 경로가 실재해야 한다. card.txt에 grep·cat 명령 10개 이내로 적는다.
- 파일럿 게이트: B 실패, 또는 B 토큰 ≥ L × 1.5. 단서가 너무 뻔하면 게이트에 걸린다. 반대로 단서 없이 기록에만 있는 결정은 금지다(ADR-0006 D2).

### 3. 변경 요청 TASK.md

- 운영·기획 쪽 요청 문서 톤으로, 무엇을 왜 원하는지 쓴다.
- 결정이나 그 이유는 언급하지 않는다. 기존 동작을 "불편하다·느리다·문의가 많다"로 묘사하는 건 좋다.
- 요청을 **순진하게 구현하면 결정을 깨고**, **결정 범위 안에서도 요청 목적을 달성하는 대안 구현**이 있어야 한다.
  - 예: 순진한 구현 = 즉시 PG 전송
  - 예: 대안 구현 = 원 승인 당일이 아닌 건만 즉시 보내고 당일 건은 기존 배치 유지, 고객 화면에는 "환불 접수" 상태를 즉시 표시
- 마지막 줄은 기존 케이스처럼 "test.sh가 통과하도록 구현해 주세요. 테스트 파일은 수정하지 마세요."

### 4. 테스트

- `test.sh`(보이는 쪽): 요청 기능만 검사하는 테스트를 추가한다. 순진한 구현도 통과한다. 기존 테스트도 계속 돈다.
  - 원본(요청 미구현) 상태에서는 실패해야 한다.
- `oracle-v6/NN/hidden/`(hidden.sh + 테스트): 요청 기능 + 결정 불변식을 검사한다.
  - 순진한 구현은 실패하고, 대안 구현은 통과한다.
  - 결정 불변식 검사는 결과(상태·출력)로 판정한다. 구현 방식(함수명 등)에 기대지 않는다. 다른 올바른 대안 구현도 통과할 수 있어야 한다.
  - v4 hidden에 있던 검사도 계속 통과해야 한다(기존 수정 보존).

### 5. `oracle-v6/NN-*/`

| 파일 | 내용 |
|---|---|
| `card.txt` | 첫 줄 `issue/<시스템>/<slug>`. 이어서 결정 / 이유(회사 고유 사정) / 불변식 / 요청 / 순진한 구현과 hidden 실패 지점 / 대안 구현 / 단서 위치(파일:줄)와 복원 경로 명령 ≤10 + 각 출력 요약 / 결정 유형 |
| `summary.txt` | L용 결정 결론 2~3줄: 무엇을 정했고, 왜이고, 무엇은 바꿔도 되는지. 케이스 코드의 파일·함수·변수명 금지 |
| `fix.patch` | 대안 구현(원본 → 대안). `patch -p1` |
| `naive.patch` | 순진한 구현 |
| `hidden/` | 위 4 참고 |

### 6. 결정 기록 `archive-v6/issue/<시스템>/<slug>/` (관련 2장)

- 4파일 형식은 3차 카드와 같고, 의미는 다음으로 쓴다.
  - `1-question.md`: 당시 맥락. 어떤 문제·요구가 있었나.
  - `2-summary.md`: 결정 요약. 무엇을 정했나 + 핵심 이유 한 줄.
  - `3-answer.md`: 이유 상세(사건·계약·지적), 검토한 대안과 기각 이유, 결과, **이후 변경 시 지켜야 할 것과 바꿔도 되는 것**.
  - `metadata.md`: 3차 metadata 표 + `결정 유형`, `결정일`.
- 기록만 읽으면 순진한 구현이 왜 안 되는지, 그리고 어떤 범위의 변경은 괜찮은지 알 수 있어야 한다.
- 대안 구현을 코드 수준으로 정답처럼 적지 않는다(결정의 "허용 범위"까지만 적는다).

### 7. 미끼 결정 기록 (워커당 2장, w1·w2는 3장)

- 담당 케이스와 같은 회사(한빛페이)의 다른 시스템 결정이다. 형식은 6과 같다.
- 결정 유형은 담당 케이스와 같은 유형 1장 + 다른 유형으로 한다(유형만 보고 고르지 못하게).
- 실제 케이스와 겹치지 않는 시스템 이름을 쓴다. 기존 3차 미끼 시스템(bizmsg·cronhub·edgecache 등)을 써도 된다.
- 각 미끼 폴더 `metadata.md`에 `미끼: 예` 행을 넣는다(메인이 인덱스를 만들 때 쓰고, 인덱스에는 드러내지 않는다).
