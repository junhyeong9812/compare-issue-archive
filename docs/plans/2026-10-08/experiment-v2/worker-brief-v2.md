# 케이스 v2 작성 워커 공통 브리핑

## 목표
1차 실험(`docs/adr/0001-*.md` 필독 — 왜 실패했는지)은 케이스가 작고(케이스당 ~100줄) 원인이 바로 보여서 에이전트가 도구 3~4번 만에 풀었고, 아카이브 효과를 잴 수 없었다. 2차 케이스는 **탐색이 필요한 작은 실제형 저장소**여야 한다(`docs/adr/0002-*.md` D2 필독).
차기 실험에서 Sonnet 에이전트가 이 케이스를 B(증상만) / F(issue 아카이브 우선) / A′(정답 카드 제공) 세 조건으로 고치고, 토큰을 비교한다.

## 규약 (1차 브리핑 `docs/plans/2026-10-08/case-build/worker-brief.md` 를 먼저 읽고, 아래 차이만 적용)
- 위치: `cases-v2/NN-name/`, `oracle-v2/NN-name/` (1차 `cases/`·`oracle/` 은 읽기만 — 수정 금지). 구조·파일(TASK.md·test.sh·card.txt·fix.patch·hidden/hidden.sh) 계약은 1차와 동일.
- 검증: `CASES_DIR=cases-v2 ORACLE_DIR=oracle-v2 ONLY=NN bash scripts/verify-cases.sh` → PASS, 3회.
- **card.txt 첫 줄에 카드 경로를 `issue/<카드경로>` 형태로** 적는다(러너가 이 경로로 A′ 프롬프트를 만든다).

## v2 난이도 요건 (전부 필수)
1. 규모: 파일 15~30개, 소스+테스트 합계 600~1,500줄. 실제 서비스처럼 계층(예: api/handler → service → repository/store → util/codec/clock)과 도메인 모델, 설정, 몇 개의 무관한 기능(노이즈)을 둔다.
2. **원인과 증상은 다른 계층·다른 파일**: 증상은 끝단(API 응답·리포트·내보내기 결과)에서 보이고, 원인은 2~3단계 아래 유틸/저장소에 있다.
3. **미끼 2개 이상**: 증상과 관련 있어 보이지만 무죄인 코드(비슷한 이름의 함수, 의심스러워 보이는 캐시/변환/정렬 코드 등). 미끼를 고쳐도 테스트가 통과하지 않아야 한다.
4. **재현 테스트는 E2E**: 공개 진입점(핸들러/서비스 퍼사드/스크립트 실행)만 호출하고, 테스트 이름·실패 메시지는 증상(사용자 관점)만 말한다. 원인 파일·함수 이름을 드러내지 않는다. 통과하는 기존 단위 테스트 몇 개를 함께 둬서 노이즈로 쓴다(test.sh는 전체 테스트를 돌리고, 재현 테스트가 실패하면 exit≠0).
5. **덜 교과서적인 변형**: 같은 카드 안에서 1차 케이스(`cases/NN-*` 와 `oracle/NN-*/card.txt` 참고)와 **다른 사건/변형**을 우선 고른다. 모델이 한눈에 "아 그 유명한 함정"이라고 알아보기 어려운 쪽. 카드에 다른 사건이 없으면 같은 사건을 더 깊이 숨겨서 쓴다(card.txt에 사유).
6. TASK.md는 운영 문의처럼 쓴다: 증상·빈도·환경·재현 명령만. 원인 방향 힌트, 카드 용어, 파일 지목 금지.
7. hidden: 1차처럼 같은 불변식을 다른 입력·경로로 검사하고, 미끼 수정이나 증상 지점 땜질(끝단에서 값 보정)로는 통과하지 못하게 한다. 그런 우회를 직접 하나 이상 적용해 hidden이 잡는지 확인하라.
