# issue/ocrid/callback-underscore-header-drop — 정답

태그: `environment-drift` · `fail-closed` · `parser-differential`

## 정답
<!-- 질문 1:1 대응 -->

1. **받지 못한다.** nginx는 `underscores_in_headers`가 기본 off라 이름에 `_`가 든 헤더를 버리고 요청은 그대로 넘긴다.\
핸들러는 서명 헤더가 없으므로 검증 실패로 `401`을 응답한다. nginx 쪽에는 오류 로그가 남지 않는다.
   > **underscores_in_headers** — nginx가 이름에 언더스코어가 든 헤더를 받아들일지 정하는 설정. 기본 off이며, 이때 그 헤더는 조용히 무시된다.

2. **신규 인그레스가 카나리로 트래픽의 30%만 받고 있었기 때문이다.**\
구 인그레스를 거친 콜백은 헤더가 살아 있어 정상 처리됐다. 실패 건은 고객 특성과 무관하게 무작위로 보였다.

3. **1분·5분·30분 간격으로 3회 재시도한 뒤 포기한다.** 재시도도 같은 비율로 신규 인그레스를 탈 수 있어, 일부는 재시도에서 살아났다.\
끝내 실패한 건의 결과는 벤더 쪽에 보관되고 `ocrid result <요청id>`로만 가져올 수 있다.\
사내 흐름은 콜백만 기다리도록 짜여 있어, 콜백이 안 오면 상태를 바꿀 계기가 없었다.

4. **401을 "벤더가 서명을 안 보냈다" 또는 "공격성 요청"으로 해석했기 때문이다.**\
처음 하루는 벤더 장애를 의심해 문의를 넣었다. 벤더는 서명을 보냈다는 송신 로그를 줬고, 그때야 수신 경로를 의심했다.\
401 비율이 인그레스 카나리 비율과 같다는 점이 결정적 단서였다.

5. **서명 검증을 끄면** 누구나 콜백 URL로 "확인 완료"를 위조할 수 있다 — 본인 확인 우회라 선택하지 않은 방법이다.\
**헤더 이름 변경 요청**은 맞는 방향이지만 벤더 릴리스 주기에 묶여 당장 쓸 수 없다. 받는 쪽 설정을 고치는 것이 즉시 가능한 대처였다.

6. **콜백 수신 로그의 상태 코드 분포를 본다.**\
4xx·5xx가 있으면 수신 쪽(인그레스·인증·핸들러) 문제다. 전부 200인데 반영이 안 됐으면 이후 처리(배치·상한·상태 전이) 쪽이다.

## 문제 구조 (추상화 코드)

### 변형 A — 인그레스 기본 설정이 콜백 헤더를 버림
① 문제 코드
```nginx
location /kyc/callback {
    proxy_pass http://kyc-app;          # underscores_in_headers 기본 off → x_ocr_sig 사라짐
}
```
② 고친 코드
```nginx
server {
    underscores_in_headers on;          # server 블록에서만 유효
    location /kyc/callback {
        proxy_pass http://kyc-app;
    }
}
```
무엇이 깨졌나: 인프라 이전에서 헤더 처리 규칙이 바뀌었고, 앱의 서명 검증이 그 결과를 fail-closed로 거절했다(거절 자체는 올바른 동작).

### 변형 B — 콜백만 기다리는 상태 전이
① 문제 코드
```java
void onCallback(Result r) { verify(r); customer.complete(r); }   // 콜백이 안 오면 영원히 진행 중
```
② 고친 코드
```java
@Scheduled(every = "5m")
void sweepPending() {
    for (Kyc k : repo.pendingOlderThan(Duration.ofMinutes(10)))
        vendor.result(k.requestId()).ifPresent(r -> { verify(r); k.complete(r); });
}
```
무엇이 깨졌나: 비동기 결과를 푸시 한 경로로만 받아, 경로 장애가 곧 영구 미반영이 됐다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| 인그레스에서 언더스코어 헤더 허용 | server 블록 단위 설정 | 작음 | 다른 location 에도 영향 | 기본(즉시) |
| 벤더에 하이픈 헤더 요청 | 벤더 릴리스 | 대기 시간 | 일정 불확실 | 장기 |
| 미수신 건 폴링 보충 | result 조회 API | 호출 수 증가 | 폴링 주기만큼 지연 | 항상 병행 |

**결론**: 수신 경로를 고치고, 콜백 방식에는 폴링 보충을 늘 함께 둔다.
