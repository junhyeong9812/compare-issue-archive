# issue/iamctl/revoke-claims-in-token — 정답

태그: `consistency` · `security`

## 정답
<!-- 질문 1:1 대응 -->

1. **허용된다.** 토큰의 `roles`에 `CUSTOMER_READ`가 남아 있고, API는 토큰만 검증한다. 14:40 만료 전까지 조회가 된다.

2. **`show`는 권한 DB를 읽기 때문이다.** 회수 자체는 즉시 반영됐지만, 이미 발급된 토큰에는 닿지 않는다.

3. **리프레시 때 권한 DB를 다시 읽어 역할이 빠진 토큰이 나온다.** 그래서 늦어도 액세스 토큰 수명(60분) 안에는 반영된다.

4. **API가 토큰 클레임 기준으로 권한을 판정하고 기록했기 때문이다.** 회수 후 38분 동안 고객 17명 조회가 '권한 있음'으로 남았다.

5. **고위험 API**: 요청마다 토큰 조회 API로 현재 권한을 확인한다(지연 5ms 수준).\
**일반 API**: 토큰 수명을 10분으로 줄이고, 회수 시 세션 폐기 이벤트로 리프레시를 막는다.

## 문제 구조 (추상화 코드)

### 변형 A — 토큰 클레임만 신뢰
① 문제 코드
```java
if (!jwt.claims().roles().contains("CUSTOMER_READ")) throw forbidden();
return customerRepo.find(id);
```
② 고친 코드
```java
if (!introspect.activeRoles(jwt.subject()).contains("CUSTOMER_READ"))   // 고위험 경로
    throw forbidden();
return customerRepo.find(id);
```
무엇이 깨졌나: 권한 판정 시점(토큰 발급)과 사용 시점(API 호출)이 최대 60분 벌어질 수 있는데 회수 경로가 이를 고려하지 않았다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| 고위험 API 요청마다 조회 | 토큰 조회 API | 지연 소폭 | 조회 서버 장애 시 차단 | 고객 원장·다운로드 |
| 토큰 수명 10분 | 리프레시 부하 | 작음 | 여전히 10분 | 일반 API |
| 회수 시 세션 폐기 | 세션 저장소 | 중간 | 이벤트 유실 | 함께 |

**결론**: 회수 반영 시간을 경로별로 정하고, 고위험 경로는 요청 시점 권한을 본다.
