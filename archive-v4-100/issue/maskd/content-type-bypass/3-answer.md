# issue/maskd/content-type-bypass — 정답

태그: `security` · `privacy`

## 정답
<!-- 질문 1:1 대응 -->

1. **하지 않는다.** 대상 목록에 `application/json`만 있었다.

2. **정상 응답의 Content-Type은 바뀌지 않았다.**

3. **같이 통과한다.** 점검에서 다운로드 오류 응답 2종이 `text/plain`으로 원문을 내는 것도 찾았다.

4. **검증 실패 메시지가 '입력값 X가 형식에 맞지 않음'처럼 요청값을 포함했다.** 주민번호 형식 검사 실패 때 원문이 들어갔다.

5. **프록시**: `*/*+json`과 `text/*`를 대상에 넣고, 모르는 형식은 차단 + 경보.\
**백엔드**: 예외 메시지에 요청값을 넣지 않는다(필드 이름만).

## 문제 구조 (추상화 코드)

### 변형 A — 허용 목록 밖은 통과
① 문제 코드
```yaml
mask:
  content_types: [application/json]
  on_unknown: pass
```
② 고친 코드
```yaml
mask:
  content_types: [application/json, "application/*+json", "text/*"]
  on_unknown: block          # 모르는 형식은 막고 경보
```
무엇이 깨졌나: 처리 대상을 좁은 허용 목록으로 두고 나머지를 통과시켜, 형식 변경이 곧 우회가 됐다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| 대상 확대 + 모르는 형식 차단 | 프록시 설정 | 작음 | 정상 바이너리 차단 | 기본 |
| 예외 메시지에서 요청값 제거 | 백엔드 수정 | 작음 | 다른 경로 | 함께 |
| 정기 응답 표본 스캔 | 스캐너 | 중간 | 표본 밖 | 안전망 |

**결론**: 보호 장치는 모르는 입력에서 닫히게(fail-closed) 둔다.
