# issue/auditsink/naive-ts-closed-index — 정답

태그: `silent-failure` · `timezone` · `environment-drift`

## 정답
<!-- 질문 1:1 대응 -->

1. **audit-0501로 가서 거부된다.** 22:30 KST로 해석돼 5월 1일 인덱스가 대상인데, 그 인덱스는 5월 2일 06:00에 봉인됐다.

2. **구 이미지는 `TZ=Asia/Seoul`이 설정돼 있었다.** 새 이미지는 TZ 환경 변수를 빼고 UTC 기본이 됐다. 로거 형식이 오프셋을 안 찍는 문제는 원래부터 있었다.

3. **00~06시는 전날 인덱스에 들어가 날짜가 틀리고, 09시 이후는 같은 날 인덱스에 9시간 이른 시각으로 들어간다.** 검색은 되지만 시각 기준 조사가 틀린다.

4. **거부 응답을 수집기가 debug로만 남겼기 때문이다.** 클라이언트는 비동기 전송이라 응답을 보지 않았다. 5월 13일 내부 감사가 특정 권한 변경 기록을 찾다 발견했다.

5. **둘 다지만 원인은 클라이언트다.** 클라이언트는 `OffsetDateTime`으로 오프셋을 찍고, 수집기는 오프셋 없는 시각을 받으면 거부 + 경보한다. 2주치 시각은 이미지 교체 시점 기준으로 +9시간 보정해 재색인했다.

## 문제 구조 (추상화 코드)

### 변형 A — 오프셋 없는 시각 직렬화
① 문제 코드
```java
String ts = LocalDateTime.now()
    .format(DateTimeFormatter.ISO_LOCAL_DATE_TIME);   // JVM TZ 따라 바뀜
```
② 고친 코드
```java
String ts = OffsetDateTime.now(ZoneId.of("Asia/Seoul"))
    .format(DateTimeFormatter.ISO_OFFSET_DATE_TIME);  // 2025-05-02T07:30:00+09:00
```
무엇이 깨졌나: 시각에서 타임존 정보를 빼고 보내, 보내는 쪽과 받는 쪽이 서로 다른 기준으로 해석했다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| 클라이언트 오프셋 포함 | 코드 수정 | 작음 | 다른 클라이언트 누락 | 기본 |
| 수집기 오프셋 없는 시각 거부+경보 | 수집기 설정 | 작음 | 구 클라이언트 거부 | 함께 |
| 봉인 거부를 경보로 승격 | 로그 수준 | 작음 | 없음 | 안전망 |

**결론**: 시각은 오프셋과 함께 보낸다. 거부는 경보로 올린다.
