# issue/idchk/vendor-maintenance-window-timeout — 정답

태그: `vendor-notice` · `timeout` · `scheduling`

## 정답
<!-- 질문 1:1 대응 -->

1. **02:00 ~ 04:00 전후 요청에 몰려 있었다.**\
미완료 611곳의 요청 시각이 전부 01:58 ~ 04:03이었다.

2. **2023년 7월 배치를 "트래픽 적은 일요일 새벽"으로 옮기면서 벤더 점검 일정을 확인하지 않았다.**\
점검 공지는 벤더 포털 공지사항에만 올라와 아무도 구독하지 않았다.

3. **점검 시작 2분 전부터 끝난 뒤 3분까지였다.**\
벤더는 점검 직전에 신규 연결을 먼저 끊고, 끝난 뒤 순차로 연다고 공지했다.

4. **래퍼가 타임아웃을 판정 결과와 같은 "미완료"로 기록했다.**\
미완료는 운영자가 수동 재요청하는 상태라 다음 달까지 방치됐다.

5. **미완료 건의 요청 시각 분포를 먼저 본다.**\
특정 시간대에 몰리면 외부 가용성 문제, 시간과 무관하게 흩어져 있으면 요청 자체나 처리 규칙 쪽을 본다.

## 문제 구조 (추상화 코드)

### 변형 A — 타임아웃을 판정 결과로 확정
① 문제 코드
```python
try:
    res = idchk_request(merchant)
except Timeout:
    res = "INCOMPLETE"            # 운영자 수동 처리 대기
save(merchant, res)
```
② 고친 코드
```python
try:
    res = idchk_request(merchant)
except Timeout:
    retry_queue.push(merchant, delay=timedelta(minutes=30))
    return
save(merchant, res)
```
무엇이 깨졌나: "벤더가 응답하지 않음"과 "확인이 끝나지 않음"을 같은 상태로 저장했다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| 배치를 점검 창 밖으로 이동 | 점검 일정 고정 | 작음 | 임시 점검 공지 | 기본 |
| 타임아웃 지연 재시도 | 재시도 큐 | 작음 | 점검 연장 시 재시도 소진 | 기본 |
| 점검 일정 캘린더 구독 | 벤더 포털 RSS | 작음 | 구독 누락 | 병행 |

**결론**: 외부 점검 창은 배치 일정의 입력이다 — 일정을 피하고, 타임아웃은 다시 시도한다.
