# issue/messaging/mqpub-batch-key-head — mqpub 한 배치 안에서 키 앞 16바이트가 같은 메시지는 첫 것만 남는다 — 질문

## 질문
1. (예측) `mqpub publish`에 키가 `settle.done.M00012345.20260801`, `settle.done.M00012399.20260801`인 두 줄을 한 번에 넣었다. 출력은 `accepted 2 batch N`이고 exit 0이다. 소비자는 몇 건을 읽는가? 왜 그런가?
2. (경계) 같은 두 키를 **서로 다른 publish 호출**로 나눠 보내면 결과가 어떻게 달라지는가? 키가 16바이트보다 짧으면 비교는 어떻게 되는가?
3. (왜) `accepted` 숫자와 `stat`의 `messages` 증가분이 다를 때, 발행 측 로그만 보는 운영자는 왜 이 손실을 알아채지 못하는가?
4. (왜) 키를 `<네임스페이스>.<이벤트>.<업무 식별자>`처럼 공통 접두로 시작하게 만드는 사내 규약이 이 동작과 만나면 무엇이 일어나는가? 손실이 "매번 다른 일부"로 보이는 이유는?
5. (경계) 고치는 방법으로 ① 메시지마다 publish를 따로 호출 ② 키 앞에 난수(UUID)를 붙임 ③ 전체 키의 결정적 해시를 키 맨 앞에 둠 — 각각 무엇을 지키고 무엇을 깨뜨리는가?
6. (연결) 이 사건을 처음 의심하고 확인할 때, 바이너리를 어떤 입력으로 몇 번 실행해 보면 규칙을 확정할 수 있는가?
7. (연결) 이 사건은 "성공 응답 ≠ 저장됨"의 한 사례다. 발행 직후 무엇을 대조하면 같은 종류의 무음 손실을 잡을 수 있는가?
