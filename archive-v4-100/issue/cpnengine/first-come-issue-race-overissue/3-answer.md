# issue/cpnengine/first-come-issue-race-overissue — 정답

태그: `concurrency` · `data-integrity` · `cost`

## 정답
<!-- 질문 1:1 대응 -->

1. **남은 수량 조회와 차감 사이에 다른 요청들이 끼어들었다.**\
같은 값을 읽은 요청이 모두 발급을 진행했다.

2. **부하 시험이 초당 300 요청이라 경합이 드물었다.**\
실제 피크는 초당 6,000이었다.

3. **고객 신뢰를 고려해 회수하지 않고 마케팅 비용으로 처리했다.**

4. **조건부 원자 차감(`UPDATE … SET remain = remain - 1 WHERE remain > 0`) 성공 시에만 발급, 발급 수 1분 단위 대사, 부하 시험은 예상 피크 기준.**

## 문제 구조 (추상화 코드)

### 변형 A — 확인 후 차감
① 문제 코드
```java
int remain = repo.remain(cpnId);
if (remain > 0) { issue(user); repo.setRemain(cpnId, remain - 1); }
```
② 고친 코드
```java
if (repo.decrementIfPositive(cpnId) == 1) {   // 원자적 조건부 차감
    issue(user);
}
```
무엇이 깨졌나: 읽기-판단-쓰기를 나눠 동시성 아래에서 한정 수량이 지켜지지 않았다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| 조건부 원자 UPDATE | 단일 DB | 작음 | 행 잠금 경합 | 기본 |
| 원자 카운터(키-값 저장소) | 저장소 가용성 | 중간 | 카운터-DB 불일치 | 대규모 |
| 발급 대기열 직렬화 | 큐 | 중간 | 응답 지연 | 대안 |

**결론**: 한정 수량은 차감이 성공한 요청만 발급한다.
