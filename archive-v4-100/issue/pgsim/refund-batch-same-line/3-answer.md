# issue/pgsim/refund-batch-same-line — 정답

태그: `silent-failure` · `identity` · `contract-drift`

## 정답
<!-- 질문 1:1 대응 -->

1. **응답은 `accepted 2`·exit 0이지만 환불은 1건이다.** stderr도 비어 있다.\
`status --batch`에는 RF 번호가 붙은 줄이 하나만 나오고, `txn TID`의 `refunded`도 9900만 늘어난다.\
벤더 `--help`는 AUX를 "optional"이라고만 적고 이 동작은 적지 않는다.
   > **AUX** — 환불 줄의 셋째 칸. 가맹점이 자유롭게 쓰는 값으로 안내되지만, 배치 안에서 같은 줄인지 가를 때 TID·금액과 함께 쓰인다.

2. **세 칸이 모두 같을 때만 합쳐진다.** 금액이 다르면 2건, AUX가 다르면 2건 환불된다.\
AUX를 둘 다 비우면 빈 값끼리 같다고 보고 1건만 환불한다.\
같은 두 줄을 배치 번호를 달리해 따로 보내면 2건 모두 환불된다 — 비교 범위는 한 호출(한 배치 파일) 안이다.

3. **배치가 보는 성공 신호(exit 0·accepted 건수)가 실제 환불 건수와 무관했다.** 정기배송 해지 배치는 남은 회차마다 `TID<TAB>회차 금액` 줄을 AUX 없이 만들었다.\
남은 회차가 2회 이상이면 금액이 같은 줄이 둘 이상 생겨 첫 회차만 환불됐고, 남은 회차가 1회인 해지는 같은 줄이 생길 수 없어 늘 맞았다.\
배치는 accepted 건수만 확인하고 해지 건을 "환불 완료"로 표시했으므로, 가맹점 정산금이 장부보다 많게 들어온 월말 PG 정산 대사에서야 차액이 드러났다.

4. **아무것도 하지 않는다.** 이미 처리한 배치 번호가 다시 오면 `pgsim`은 파일을 보지 않고 `accepted N`만 낸다(exit 0).\
그래서 누락 줄만 같은 배치 번호로 다시 보내면 또 조용히 무시된다.\
재처리는 새 배치 번호로 하고, 그 배치 안에서도 줄마다 AUX를 다르게 해야 한다.

5. **배치 단위 대사와 항목별 환불 증빙이 깨진다.** 금액을 합친 한 줄은 RF 번호가 하나라 회차·상품별 환불 번호를 줄 수 없고, 부분 취소·이의 제기 때 금액을 다시 나눠야 한다.\
줄마다 배치를 나누면 PG 정산 파일과 우리 회차(배치 번호)의 1:1 대응이 깨지고 호출 수도 줄 수만큼 는다.\
규칙이 보는 것은 AUX이므로, 구성을 바꾸지 말고 AUX만 줄마다 다르게 채우면 된다.

6. **accepted는 파일 접수 증빙일 뿐이다.** 완료 판정은 `status --batch`의 RF 줄 수가 보낸 줄 수와 같은지, 원거래별 `txn`의 refunded 증가분이 보낸 금액 합과 같은지로 한다.\
근본 대처는 AUX를 채워 합쳐짐 자체를 막는 것이고, 조회 대사는 규칙이 바뀌거나 다른 경로에서 같은 일이 생길 때를 위한 안전망이다.
   > **결정적 식별자** — 같은 줄을 다시 만들면 늘 같은 값이 나오는 식별자(예: 주문번호-회차). 난수와 달리 로그·정산 파일에서 추적할 수 있다.

## 문제 구조 (추상화 코드)

### 변형 A — AUX 없이 같은 금액 회차를 한 배치로 환불 (정기배송 해지)
① 문제 코드
```java
for (Installment i : sub.remaining())                       // 남은 회차: 9900, 9900, 9900
    file.add(sub.tid() + "\t" + i.amount());                  // AUX 없음 → 세 줄이 같은 줄
int accepted = pg.refund(mid, batchId, file);                 // "accepted 3", exit 0 — 환불은 1건
if (accepted == file.size()) sub.markRefunded();              // 완료로 오인
```
② 고친 코드
```java
for (Installment i : sub.remaining())
    file.add(sub.tid() + "\t" + i.amount() + "\t" + sub.no() + "-" + i.seq());   // 줄마다 다른 결정적 AUX
pg.refund(mid, batchId, file);
```
무엇이 깨졌나: PG는 배치 안의 (TID, 금액, AUX)가 같은 줄을 재전송으로 보는데, 호출부가 줄을 구별할 값을 넣지 않았다.

### 변형 B — 주문 단위 참조를 AUX에 넣음 (배송비 환불)
① 문제 코드
```java
line.aux = order.no();                                        // 같은 주문의 줄은 AUX가 모두 같다
// 묶음 배송 2건의 배송비 3000, 3000 → 같은 줄로 합쳐져 3000만 환불
```
② 고친 코드
```java
line.aux = order.no() + "-" + shipment.seq();                 // 환불 단위(배송 건) 식별자까지
```
무엇이 깨졌나: AUX가 채워져 있어도 환불 단위보다 넓은 식별자(주문)라 같은 금액 줄을 구별하지 못했다.

### 변형 C — accepted로 완료를 판정함 (대사 누락)
① 문제 코드
```java
if (pg.refund(mid, b, file) == file.size()) markAllDone();    // accepted = 줄 수일 뿐
```
② 고친 코드
```java
pg.refund(mid, b, file);
List<Row> rows = pg.status(b);                                // RF 번호가 붙은 줄만 실제 환불
if (rows.size() != file.size()) alert("refund rows " + rows.size() + "/" + file.size() + " in " + b);
```
무엇이 깨졌나: 벤더 성공 신호를 실제 처리 결과 대신 썼다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| 줄마다 결정적 AUX | 규칙(같은 3칸 → 1건)을 안다 | 작음 | AUX 24자·문자 제한 넘김(E16) | 모든 환불 배치 — 기본 |
| 같은 TID 줄을 금액 합계 1줄로 | 항목별 환불 번호가 필요 없음 | 작음 | 항목별 증빙·부분 이의 처리 불가 | 선택하지 않은 방법 |
| 줄마다 배치 분리 | 배치 단위 대사를 포기 | 큼(호출 수) | 배치-회차 대응 깨짐 | 선택하지 않은 방법 |
| status/txn 사후 대사 | 조회 권한 | 중간 | 합쳐짐 자체는 막지 못함 | AUX와 함께 안전망 |

**결론**: AUX를 줄 식별자로 채우는 것이 근본 대처이고, status/txn 대사는 같은 종류의 조용한 누락을 잡는 안전망이다. 둘을 함께 둔다.
