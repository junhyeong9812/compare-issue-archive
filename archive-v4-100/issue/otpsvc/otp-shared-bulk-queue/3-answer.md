# issue/otpsvc/otp-shared-bulk-queue — 정답

태그: `resource-isolation` · `latency`

## 정답
<!-- 질문 1:1 대응 -->

1. **19:07 무렵 나간다.** 앞의 마케팅 40만 건이 먼저 소진된다.

2. **API는 큐에 넣는 순간 응답한다.** 발송 시각은 큐 처리 속도에 달려 있다.

3. **대기가 3분을 넘으면 도착한 번호는 이미 만료다.** 이날 19~20시 인증 실패율이 평소 2%에서 31%로 올랐다.

4. **문자 발송 공용 모듈이 otpsvc 클라이언트를 감싼 것이었다.** 마케팅팀은 같은 모듈을 가져다 썼고, 큐 설정은 들여다보지 않았다.

5. **인증번호 전용 큐 + 전용 발송사 계정, 마케팅은 별도 큐(promo)와 시간당 상한.** 큐 대기 p95가 30초를 넘으면 경보.

## 문제 구조 (추상화 코드)

### 변형 A — 단일 큐
① 문제 코드
```yaml
queues:
  sms: { rate: 1000/s }        # 인증·마케팅 공용
```
② 고친 코드
```yaml
queues:
  otp:       { rate: 300/s, account: otp-dedicated }
  promo:     { rate: 700/s, max_per_hour: 1500000 }
alerts:
  otp_queue_wait_p95: 30s
```
무엇이 깨졌나: 지연에 민감한 트래픽과 대량 트래픽이 자원을 공유해, 대량 쪽이 민감한 쪽의 시간 예산을 다 썼다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| 전용 큐·계정 분리 | 발송사 계정 추가 | 중간 | 계정 비용 | 기본 |
| 우선순위 큐 | 큐 엔진 지원 | 작음 | 발송사 쪽 대기는 못 막음 | 보조 |
| 마케팅 시간대 제한 | 운영 합의 | 작음 | 캠페인 반발 | 함께 |

**결론**: 인증번호는 시간 예산이 있는 트래픽이다. 자원을 분리하고 대기 시간을 본다.
