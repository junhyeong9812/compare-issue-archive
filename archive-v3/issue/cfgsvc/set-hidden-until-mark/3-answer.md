# issue/cfgsvc/set-hidden-until-mark — 정답

태그: `silent-failure` · `contract-drift` · `single-source-of-truth`

## 정답
<!-- 질문 1:1 대응 -->

1. **이전 값이 나온다.** `limit.m1042.daily`는 이미 값이 있던 키라, set이 exit 0과 변경 번호를 출력해도 get은 마지막 `mark` 때의 값을 준다.\
`keys limit.`은 `키 변경번호 st`를 탭으로 출력하는데, 방금 바꾼 키는 변경 번호가 새 번호로 바뀌어 있고 st가 `3`이다.\
get에 보이는 키는 st `0`이다. 벤더 `--help`에는 이 동작이 없고 stderr도 비어 있다.
   > **st 3** — 서비스가 변경을 받아 두었지만 아직 get에 내주지 않는 상태. 벤더 문서에 없는 동작이다.

2. **새 키는 바로 보이고, 기존 키는 mark 뒤에 보인다.** 처음 만드는 키는 set 직후 get이 방금 값을 준다(st는 똑같이 `3`).\
기존 키를 두 번 set해도 get은 여전히 마지막 mark 때의 값이고, mark 뒤에는 마지막으로 set한 값이 보인다.\
`cfgsvc mark` 한 번이면 그때까지 쌓인 모든 키의 변경이 보이고 st가 `0`이 된다.

3. **신규 가맹점 한도는 새 키였다.** 콘솔은 변경 직후 get으로 "반영 확인"을 했는데, 기존 가맹점의 한도 키는 이전 값을 돌려줘 "반영 실패"로 표시됐다.\
신규 가맹점 등록은 처음 만드는 키라 set 직후 get이 바로 새 값을 줬고, 그래서 늘 "성공"이었다.\
운영자가 "실패"를 보고 같은 변경을 여러 번 다시 누르면서 같은 키에 변경 번호만 쌓였다(값은 같아 피해는 없었지만, 감사 기록이 지저분해졌다).

4. **mark는 그때까지의 변경을 get에 보이게 만든다.** 출력은 마크 번호(`M…`)뿐이고, 변경이 있었으면 번호가 1 오른다.\
변경이 없을 때 부르면 같은 번호를 다시 출력할 뿐 아무것도 바뀌지 않는다 — 그래서 여러 번 불러도 안전하다.\
야간 정산 배치가 "설정 스냅샷 번호"를 기록하려고 `mark`를 부르고 있었고, 그 순간 낮에 바꾼 한도들이 보이기 시작했다 — 다음 날 아침에는 값이 맞아 있던 이유다.
   > **마크** — 서비스가 get에 내주는 값의 기준점. 이름은 조회처럼 보이지만 기준점을 앞으로 옮기는 명령이다.

5. **화면만 맞고 실제로 값을 읽는 쪽은 여전히 이전 값이다.** 결제 서버는 한도를 get으로 읽는다.\
콘솔이 자기가 set한 값을 보여 주면 "반영 실패" 표시는 사라지지만, 다음 mark(야간 배치)까지 결제 서버는 이전 한도로 승인했다.\
게다가 운영자가 서비스에 직접 넣은 다른 값과 콘솔 화면이 어긋날 수 있다 — 기준은 서비스가 get으로 내주는 값이어야 한다.

6. **set 묶음이 끝난 직후, 읽기 전에 mark를 부른다.** 검증·렌더·캐시 적재처럼 set한 결과를 같은 서비스에서 다시 읽는 단계 앞이다.\
읽은 값으로 다시 검증하는 단계는 같은 시점에 같은 이전 값을 읽으므로 "일치"로 통과한다 — 이 문제를 잡지 못한다.\
확인하려면 읽기 전에 `keys`에 st `3`이 남아 있지 않은지 보거나, 바꾼 키를 get해 set한 값과 대조한다(mark 뒤).

## 문제 구조 (추상화 코드)

### 변형 A — set 직후 get으로 "반영 확인" (운영 콘솔)
① 문제 코드
```java
config.set(key, newLimit);                         // exit 0, 변경 번호
String now = config.get(key);                      // 기존 키 → 마지막 mark 때의 이전 값
screen.show(now.equals(newLimit) ? "반영됨" : "반영 실패");   // 기존 키는 늘 "반영 실패", 새 키는 "반영됨"
```
② 고친 코드
```java
config.set(key, newLimit);
config.mark();                                     // 변경을 get 에 보이게 한다 (변경 없으면 무해)
String now = config.get(key);
screen.show(now.equals(newLimit) ? "반영됨" : "반영 실패");
```
무엇이 깨졌나: 서비스는 기존 키의 변경을 다음 mark 전까지 get에 내주지 않는데, 호출부는 set 직후 get을 "현재 값"으로 믿었다.

### 변형 B — 자기가 set한 값을 보여 준 1차 조치
① 문제 코드
```java
config.set(key, newLimit);
screen.show("반영됨 (" + newLimit + ")");            // 화면은 맞다
// 결제 서버: config.get(key) → 여전히 이전 값 (다음 mark 까지)
```
② 고친 코드
```java
config.set(key, newLimit);
config.mark();                                     // 읽는 모든 쪽(결제 서버 포함)에 보이게
screen.show("반영됨 (" + config.get(key) + ")");
```
무엇이 깨졌나: 증상(화면 표시)만 덮었다 — 서비스 값을 읽는 실제 소비자는 여전히 이전 값을 썼다.

### 변형 C — 같은 서비스를 다시 읽는 검증
① 문제 코드
```java
for (String k : changed) config.set(k, values.get(k));
render(config::get);                               // 이전 값으로 렌더
verify(config::get);                               // 같은 이전 값과 비교 → "일치"
config.mark();                                     // 기록용으로 마지막에만 — 이제야 보임
```
② 고친 코드
```java
for (String k : changed) config.set(k, values.get(k));
config.mark();                                     // 읽기 전에
render(config::get);
verify(config::get);
```
무엇이 깨졌나: mark를 기록용 조회로 여겨 맨 끝에 두었다 — 렌더와 검증이 모두 이전 값을 읽어 서로 일치했고, 끝난 뒤 조회하면 새 값이 보여 원인을 더 찾기 어려웠다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| set 묶음 뒤 읽기 전에 mark 1회 | 벤더 규칙(기존 키는 mark 전까지 안 보임)을 안다 | 작음 | 다른 사람이 set만 해 둔 변경도 함께 보이게 된다 | 기본 — 읽는 쪽이 서비스 값을 기준으로 삼을 때 |
| set할 때마다 mark | 같음 | 호출 수 증가 | 묶음 중간 상태가 다른 소비자에게 보인다 | 키 하나씩 바꾸는 화면 |
| 자기가 set한 값을 로컬에서 덮어 씀 | 서비스를 다시 읽지 않음 | 작음 | 실제 소비자는 이전 값, 서비스에 직접 넣은 값 누락 | 선택하지 않은 방법 |
| 읽기 전에 `keys`의 st 3 확인 + 알림 | 조회 권한 | 중간 | 늦음 자체는 막지 못함 | mark와 함께 안전망으로 |

**결론**: 변경을 읽어 쓰는 경로 앞에 mark를 두는 것이 근본 대처이고, `keys`의 st 확인은 다른 경로가 mark를 빠뜨렸을 때 알아채는 안전망이다.
