# issue/order-alerts/carrier-reject-no-resend — 이유·대안·결과

태그: `duplicate-send` · `vendor-contract` · `retry`

## 이유 상세
1. **사건(INC-0719, 2025-07-19).** 여름 프로모션 회차에서 E-THROTTLE·E-CARRIER 실패가 수백 건 나왔고, 1.8.0 재발송이 다음 회차에 이들을 다시 보냈다. 이후 "같은 문자 두 통" 민원 312건.\
   대행사 발송·과금 내역에는 해당 고객마다 2건씩 발송 성공이 남아 있었다. 두 번째는 모두 우리 재발송분이었고, 첫 번째는 우리 리포트에 "실패"로 찍힌 건이었다.
2. **대행사 회신(2025-08-05) — 계약 부속서 3장 해석.**
   - `E-THROTTLE`: 요청을 받지 않은 것으로 처리한다. 대기열에 넣지 않고 과금도 없다.
   - `E-CARRIER`: 대행사가 대기열에 남겨 두었다가 통신사 반려가 풀리면 같은 메시지를 다시 넣는다(30분 안, 1회). 이 재전송 결과는 요청자에게 통보하지 않는다(콜백 없음). 성공하면 1건 과금.
   - 즉 민원 312건은 전부 `E-CARRIER` 건이었다. `E-THROTTLE` 재발송분에서는 중복이 없었다.
3. 1.9.0(2025-07-28)은 회신 전 임시 조치로, 사유를 가리지 않고 재발송 목록을 비웠다. 회신 뒤 재설계는 백로그로 남았다.

## 검토한 대안
| 대안 | 기각 이유 |
|---|---|
| 1.8.0 그대로(두 사유 모두 재발송) | 사건 재현. E-CARRIER는 대행사 재전송과 겹친다. |
| E-CARRIER를 30분 뒤에만 재발송 | 대행사 재전송 성공 여부를 알 길이 없다(통보 없음). 30분 뒤에도 겹칠 수 있다. |
| 대행사 재전송 기능을 끄도록 계약 변경 | 대행사 표준 약관 조항이라 개별 변경 불가(회신). |
| E-CARRIER 건을 리포트에 별도 상태로 표시 | 괜찮다 — 재발송이 아니라 표시만이면 결정과 충돌하지 않는다. |

## 결과
- 1.9.0 이후 같은 유형 중복 민원 없음.
- 부작용: E-THROTTLE 실패도 재발송되지 않아, 프로모션 회차마다 CS팀이 수동 재발송 중(알려진 불편).

## 이후 변경 시
- **지켜야 할 것**: `E-CARRIER`로 실패한 알림을 우리 쪽에서 대행사에 다시 요청하지 않는다(재발송·수동 재처리 도구 모두).
- **바꿔도 되는 것**: `E-THROTTLE`처럼 대행사가 받지 않은 것으로 처리하는 사유는 다음 회차 재발송 대상으로 넣어도 된다. 표시·집계(리포트 상태 구분 등)는 자유.
- 새 실패 코드가 생기면 재발송 대상에 넣기 전에 대행사 처리 방식(부속서 3장)을 먼저 확인한다.
