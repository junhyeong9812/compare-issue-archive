# issue/rollout/unchanged-host-config-kept — 이유·대안·이후 변경

태그: `cost` · `deploy` · `db-connections`

## 답
1. **그 달 최대 동시 커넥션 수의 구간(600 이하 / 1,200 이하 / 1,200 초과).** pay-db 계약(2025 갱신분 별표 2) 조건이다. 한 번 올라간 구간은 그 분기 끝까지 유지되므로, 1~2분짜리 피크 하나가 석 달 요금을 정한다. 평시 최대는 700대(1,200 이하 구간)다.

2. **헤더 한 줄도 "내용 변경"이라 전 서버가 한꺼번에 재기동했다.**
   - 에이전트는 파일의 sha256만 본다. 헤더의 릴리스 id가 바뀌면 값이 같아도 재기동한다(mtime만 바뀌는 것은 무시).
   - graceful restart는 새 프로세스가 커넥션 풀을 다 연 뒤 옛 프로세스가 풀을 닫는다 — 서버마다 약 40초 동안 풀이 두 개다.
   - 에이전트 폴링 주기가 같아서 전 서버가 같은 분 안에 재기동했고, 풀 크기(16~40) × 약 60대 × 2가 겹쳐 1,310이 됐다.

3. **값이 같으면 파일을 건드리지 않는다.**
   - 렌더 결과를 기존 파일과 헤더를 뺀 나머지로 비교해, 같으면 기존 파일을 그대로 둔다(헤더도 옛 릴리스 그대로).
   - 다르면 새 파일로 바꾼다 — 이때만 그 서버가 재기동한다.
   - 이 때문에 헤더의 릴리스가 서버마다 다를 수 있다. "이번 배포를 받았는가"는 헤더가 아니라 배포 이력으로 확인한다.

4. **검토한 대안**

| 대안 | 기각 이유 |
|---|---|
| 헤더에서 릴리스 id 제거하고 매번 다시 쓰기 | 내용이 같으면 해시가 같아 재기동은 없지만, 값이 바뀐 서버를 헤더로 구분할 수 없게 됨. 결국 "값이 같으면 그대로"와 같은 효과라 비교 방식으로 정리 |
| 배포를 존(a/b)별로 시차 적용 | 값이 바뀐 서버가 많을 때 피크를 낮추는 효과는 있으나 바뀌지 않은 서버의 재기동 자체를 없애지 못함. 후속 과제로 보류 |
| 에이전트를 reload 방식으로 변경 | 앱이 설정 다시 읽기를 지원하지 않음(앱팀 일정 미정) |
| pay-db 계약 구간 상향 수용 | 분기당 추가 요금이 연간 플랫폼 예산 초과 — DB팀 반대 |

5. **이후 변경 시**
   - 지킬 것: 배포 뒤 설정 값이 바뀌지 않은 서버의 `app.conf`는 **바이트 단위로 그대로**여야 한다. 헤더·주석·공백 같은 "값 아닌 부분"을 바꾸는 것도 재기동을 부른다. 값이 바뀐 서버만 파일이 바뀐다.
   - 바꿔도 되는 것: 배포 상태·릴리스 표시를 에이전트가 보지 않는 곳에 두는 것(배포 이력, 같은 폴더의 다른 파일, 조회 명령의 출력 형식 등), 값이 바뀐 서버의 헤더 형식, 비교 방식(값만 비교하든 헤더 뺀 전체를 비교하든 결과가 같으면 됨).
   - 에이전트가 reload를 지원하거나 pay-db 요금 체계가 바뀌면 이 결정을 다시 연다 — DB팀·플랫폼팀 확인 필요.

## 결과
- 2025-08 이후 pay-db 최대 동시 커넥션 700대로 복귀, 4분기부터 원래 구간.
- 부작용: 운영자가 헤더만 보고 "이번 배포에서 빠진 서버"로 오해하는 문의가 계속 나온다(표시 개선은 후속 과제).
