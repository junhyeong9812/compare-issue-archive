# issue/idchk/batch-head-cutoff — 정답

태그: `silent-failure` · `resource-bounding` · `contract-drift`

## 정답
<!-- 질문 1:1 대응 -->

1. **앞 12건만 볼 수 있다.** `batch`는 20줄을 모두 읽었다고 출력하지만 판정은 파일의 1~12번째 줄에만 저장한다.\
13~20번째 줄의 `result`는 `E31`(exit 3)이다.\
`job J0000001`은 `in 20`과 판정별 건수 `v1`·`v2`를 보여 주는데, 그 합이 12다 — 버림이 드러나는 유일한 출력이다.\
벤더 `--help`에는 이 동작이 없고 stderr도 비어 있어서, 호출부는 20건 접수로 받아들인다.

2. **호출당 앞 12줄.** 12줄은 전부 판정, 13줄은 앞 12줄 판정·13번째 버림, 30줄은 앞 12줄 판정·18줄 버림.\
버려지는 줄은 내용과 무관하고 파일 안의 위치(13번째 이후)로만 정해진다.\
그래서 파일을 어떤 순서(번호순·이름순)로 쓰느냐에 따라 "버려지는 사람"이 무작위처럼 보인다.\
형식 검사는 버리기 전에 전체 줄에 대해 하므로, 형식이 틀린 줄이 하나라도 있으면 파일 전체가 E13~E17로 거부된다(이건 시끄러운 실패).

3. **줄 수 확인이 버림을 보지 못했다.** 정기 재확인 배치는 2024년 3월 월초에 대상 가맹점 대표자 전체(수십 건)를 한 파일로 보냈다(당시 idchk 3.2.x).\
벤더가 돌려주는 줄 수는 "읽은 줄 수"라서 보낸 줄 수와 항상 같았고, 종료 코드도 0이었다.\
13번째 줄 이후 가맹점은 판정이 없어 "재확인 미완료"로 남았고, 정산 시스템이 그 가맹점들의 정산을 보류했다.\
다음 날 배치는 "보낸 적 있는 요청"을 다시 보내지 않고 결과만 다시 조회했으므로 계속 E31이었다.\
발견은 가맹점 문의("재확인을 했는데 정산이 보류됐다")였다.

4. **영구 대기가 된다.** 판정이 없는 이유가 "처리 중"이 아니라 "버려짐"이라 아무리 기다려도 결과가 오지 않는다.\
`idchk`는 판정을 batch 호출 안에서 바로 저장한다 — 판정된 요청은 호출 직후부터 `result`가 나온다.\
그러므로 batch 직후 `result`가 `E31`이면 그 요청은 처리되지 않은 것이다. `job`의 v1 + v2 < in으로도 확인된다.
   > **E31** — `result`에 해당 참조의 판정이 없다는 뜻. 처리 중 상태 코드가 아니다.

5. **다시 보내면 정상 판정된다.** 버려진 줄만 모아 12줄 이하로 다시 batch하면 새 job으로 판정이 저장된다.\
이미 판정된 요청을 다시 보내도 같은 입력이면 같은 판정이 다시 저장될 뿐이다(마지막 판정이 `result`에 나온다).\
다만 벤더 호출 건수가 늘어나므로, 재전송은 E31로 남은 요청만 대상으로 한다.

6. **호출 단위는 12줄 이하, 확인 단위는 요청 하나.** 배치는 대상 전체를 12줄 이하 묶음으로 나눠 묶음마다 batch를 호출한다.\
"판정됐다"는 요청마다 `result`가 나오는 것으로 판정하고, 접수 응답(job id·줄 수)은 "보냈다"의 증빙으로만 쓴다.\
안전망으로 batch 직후 `job`의 v1 + v2가 in과 같은지 확인하면, 분할 코드가 빠진 호출부도 바로 드러난다.

## 문제 구조 (추상화 코드)

### 변형 A — 대상 전체를 한 파일로 보냄 (정기 재확인 배치)
① 문제 코드
```java
List<Request> reqs = targets.stream().map(Request::of).toList();   // 수십 건
Ticket t = idchk.batch(reqs);                                      // 앞 12줄만 판정, exit 0
if (t.lines() != reqs.size()) throw new VendorException();         // 읽은 줄 수 = 전체 → 통과
targets.forEach(x -> x.markSent(t.jobId()));
```
② 고친 코드
```java
static final int BATCH_LINES = 12;                                 // 벤더 호출당 판정 상한
for (int i = 0; i < reqs.size(); i += BATCH_LINES) {
    List<Request> chunk = reqs.subList(i, Math.min(i + BATCH_LINES, reqs.size()));
    Ticket t = idchk.batch(chunk);
    chunk.forEach(r -> targets.byRef(r.ref()).markSent(t.jobId()));
}
```
무엇이 깨졌나: 벤더는 호출당 12줄까지만 판정하는데 호출부는 대상 전체를 한 번에 보냈고, 줄 수 에코를 처리 건수로 믿었다.

### 변형 B — E31을 "처리 중"으로 해석해 재전송하지 않음 (같은 사건의 다음 날 배치)
① 문제 코드
```java
for (Target x : targets.sent()) {
    Optional<Integer> v = idchk.result(x.ref());   // E31 → empty
    if (v.isEmpty()) continue;                     // "아직 처리 중" — 다음 날 다시 조회만
    x.apply(v.get());
}
```
② 고친 코드
```java
List<Target> lost = targets.sent().stream().filter(x -> idchk.result(x.ref()).isEmpty()).toList();
resend(lost);                                      // 변형 A의 12줄 분할로 다시 batch
```
무엇이 깨졌나: 판정은 batch 안에서 즉시 저장되므로 E31은 "버려짐"인데, 호출부는 비동기 처리 중으로 보고 기다리기만 했다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| 호출당 12줄 이하 분할 | 벤더 상한(12줄)을 안다 | 작음(호출 수 증가) | 분할 크기를 12보다 크게 잡으면 다시 버림 | 모든 batch 호출부 — 기본 |
| batch 후 E31만 재전송 반복 | result 조회 가능 | 중간(조회·재호출) | 루프 종료 조건을 잘못 두면 무한 재시도 | 분할을 넣기 어려운 호출부·안전망 |
| 한 건씩 batch | 없음 | 큼(호출 수 = 건수) | 대량일 때 느림 | 건수가 아주 적을 때 |

**결론**: 12줄 분할이 근본 대처이고, batch 직후 `job`의 v1 + v2 = in 확인(또는 E31 재전송)을 안전망으로 함께 둔다.
