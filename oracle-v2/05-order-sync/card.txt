채택 사건: 3-answer.md 정답 3 / 변형 B — tip만 검사하는 오프셋 커서
  "커서는 첫 원소(tip)만 같은지 봤다. 이미 넘겨준 구간 안에서 브랜치가 삭제되면(tip 은 그대로) 목록이 앞으로 당겨져 offset 이 가리키는 위치가 밀린다."
  "깨지는 조건은 "tip 변경"이 아니라 "이미 받은 구간의 길이 변경"이며 ... 전부 tip 검사를 통과한다."
  "커서에 둘 다 싣고, 불일치 시 명시적 에러를 낸다(조용히 이어붙이지 않는다)"
1차와의 차이: 1차(05-order-export)는 변형 C(keyset 스캔 뒤 삭제 필터 → 필터 뒤 개수로 조기 종료). v2는 같은 카드의 변형 B(오프셋 커서의 tip-only 검증 → 넘겨준 구간 길이 변화를 무음 흡수)로 바꿨다. "필터 뒤 개수" 류의 알려진 함정이 아니라, 이미 '변경 감지'가 있어 보이는 코드의 감지 범위 결함이다.
근본 원인: orderfeed/util/page_token.py — 토큰이 offset + top(목록 맨 위 주문, 카드의 tip)만 싣고 ensure_current()가 top만 비교한다. 이미 넘겨준 구간에서 취소(삭제)·과거 시각 POS 반입(삽입)이 일어나면 tip은 그대로라 통과하고 offset이 밀려 주문이 무음 유실된다. 증상은 client/sync_client.fetch_all 결과(끝단).
올바른 해결: 토큰에 seam(직전 페이지 마지막 주문 id)을 함께 싣고, 다음 페이지 요청 때 현재 목록의 offset-1 위치 id와 tip·seam을 둘 다 비교해 불일치면 StaleCursor(409) — 클라이언트의 기존 재시작 경로가 처리한다(feed_service.page + page_token 두 파일). 기존 단위 테스트(PageToken 2인자 생성)를 깨지 않도록 seam은 기본값을 둔다.
미끼: client/sync_client의 seen 중복 제거·재시작 루프(무죄), page_token의 base64 패딩 처리(무죄), store/order_store.active_between의 tie-break 없는 ORDER BY(리포트 전용, 무죄), report_service의 시간대 버킷팅(무죄), 이미 있는 tip 검사(일부만 맞음 — 새 주문·최신 주문 취소는 정상이라 "감지는 된다"고 오인하게 함).
hidden: 과거 시각 POS 반입(삽입), 같은 간격 안 취소+반입(총 개수 불변 — count 검사 우회를 잡음), seam 주문 자체 취소, 3페이지 뒤 2페이지 구간 취소, 클라이언트 없이 API 직접 순회("에러 없이 끝났다면 완전해야 한다" — 클라이언트 쪽 사후 대조 땜질을 잡음).
