채택 사건: 질문 2 / 정답 2 / 변형 B 앞부분 (static 초기화 순서) — 1차(변형 B 뒷부분, 인자 평가 순서)와 다른 사건
  인용: "static 필드는 **소스 선언 순서**대로 초기화된다. 자기 자신 인스턴스를 만드는 필드가 그 생성자가 쓰는 필드보다 먼저 오면 null을 본다."
  인용: "(역참조하지 않고 보관만 하면 예외 없이 null을 품은 인스턴스가 남아 나중에 터진다)"
  변형 사유: 카드의 원 사건은 참조 필드(null → NPE/ExceptionInInitializerError, 즉 시끄러운 실패)다. v2는 같은 규칙을 원시 int 필드로 옮겨 "보관만 하는" 조용한 쪽으로 숨겼다 — 생성자가 아직 초기화 전인 static int(기본값 0)를 인스턴스 필드에 복사한다. 값은 Settings 호출이라 컴파일 타임 상수가 아니어서 인라인되지 않는다.
근본 원인: domain/PasswordPolicy 에서 `DEFAULT = new PasswordPolicy()`가 `REUSE_WINDOW = SETTINGS.intValue(...)`보다 위에 선언되어, 생성자가 REUSE_WINDOW 를 0 으로 읽는다 → 재사용 금지 창 0 → 최근 비밀번호 재사용이 전부 허용된다(증상은 api 의 PUT /me/password 200).
올바른 해결: REUSE_WINDOW 선언을 DEFAULT 위로 옮긴다(의존되는 static 먼저, 인스턴스 나중). 지연 홀더 등 초기화 순서를 고정하는 다른 방법도 hidden 통과.
미끼: service/PasswordHistoryGuard(window<=0 조기 반환·해시 비교), crypto/PasswordHasher(매번 다른 salt → 해시 동등 비교가 틀려 보임), store/CredentialHistoryStore(trim·recent 인덱스 계산), config/Settings(trim·폴백·시스템 프로퍼티 덮어쓰기).
hidden: -Dpassword.reuseWindow=5(기본)/3/1 세 JVM 으로 사용자 변경·관리자 리셋 두 경로에서 "창 안 거절·창 밖 허용"을 검사 → 값 하드코딩(예: Math.max(window,5)) 땜질을 잡는다.
