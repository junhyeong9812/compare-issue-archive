현재 규칙(바이너리): set은 exit 0·변경 번호를 주지만, 마지막 mark 때 이미 값이 있던 키는 다음 mark 전까지 get이 이전 값을 준다(새 키는 바로 보임, keys st 3 = 대기). 대처 = set 묶음 뒤, 읽기(렌더) 전에 mark.
낡은 규칙(카드): 보류되는 것은 마지막 mark 뒤 이미 변경이 들어간 키의 재변경뿐이고, mark 뒤 첫 set은 기존 키도 바로 보인다(st 0). 대처 = set 묶음 앞에서 mark로 보류를 비우고 같은 키는 한 번만 set.
  같은 메커니즘(mark가 get 노출 기준점)·조건만 다름(보류 대상: "mark 때 값이 있던 키" ↔ "mark 뒤 이미 바뀐 키") → 대처 위치가 set 뒤 ↔ set 앞.
  낡은 카드를 따른 수정(stale-fix.patch: 20-apply 루프 앞 mark)은 오류 없이 돌지만 기존 키 변경이 렌더에 안 보인다 → test·hidden 모두 실패.
근본 원인: steps/20-apply.sh — 변경을 set만 하고 mark 없이 다음 단계(30-render)가 get으로 렌더한다. mark는 맨 끝 50-record(이력용)에서만 부른다.
올바른 해결(v3와 같음): apply 단계에서 set을 모두 한 뒤 cfg_mark(= cfgsvc mark)를 부른다(fix.patch). render 전에 mark가 set 뒤에 오기만 하면 된다.
