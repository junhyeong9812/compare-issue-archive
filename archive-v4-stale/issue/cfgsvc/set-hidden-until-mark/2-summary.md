# issue/cfgsvc/set-hidden-until-mark — 정리 (힌트)

태그: `silent-failure` · `contract-drift` · `single-source-of-truth`

## 전체 흐름 (cfgsvc 1.8.x 기준)

```
호출부 ──set KEY V──▶ cfgsvc ──▶ journal (변경 번호 C…, exit 0, stderr 없음)
                         │
   KEY 에 마지막 mark 뒤의 변경이 아직 없다   │ get KEY → 방금 set한 값 (바로 보임)     keys: st 0
     (기존 키의 그날 첫 변경 · 처음 만드는 키)  │
   KEY 에 마지막 mark 뒤의 변경이 이미 있다   │ get KEY → 그 앞의 값 (이번 set은 안 보임) keys: st 3
     (같은 키 두 번째 변경부터)               │
                         │
              cfgsvc mark ──▶ 보류된 변경이 get 에 보인다 → keys: st 0, 마크 번호 +1
              (변경이 없으면 같은 마크 번호만 다시 출력 — 부작용 없음)

  운영 콘솔                                   야간 정산 배치
  그날 첫 변경   → get(새 값) → "반영됨"          ... → mark (스냅샷 번호 기록용) → 이때 보류분이 보임
  같은 날 재변경 → get(앞의 값) → "반영 실패" → 운영자 재시도 → 보류만 쌓임

잘못된 교정: 콘솔이 자기가 set한 값을 화면에 표시 → 화면만 맞고, get 으로 읽는 결제 서버는 여전히 앞의 값
올바른 교정: set 묶음을 넣기 전에 mark 를 한 번 불러 보류를 비운다 — 그 뒤의 set 은 바로 보인다
발견 방법:   keys 의 st (3 = 보류, 0 = 보임) · set 직후 get 이 방금 값인지 직접 확인
```

## 핵심 문장

- `cfgsvc set`은 언제나 exit 0·변경 번호를 주지만, **마지막 `mark` 뒤 이미 변경이 들어간 키는 다음 `mark` 전까지 `get`이 그 앞의 값**을 준다.
- **mark 뒤 첫 set은 바로 보인다** — 기존 키의 첫 변경도, 처음 만드는 키도 정상이고, 같은 키를 다시 바꾼 변경만 조용히 늦는다.
- `mark`는 도움말에 "현재 마크 출력"으로만 적혀 있지만, 부르면 **보류된 변경을 get에 보이게** 만든다. 변경이 없으면 번호만 다시 출력한다.
- 대처: **set 묶음을 넣기 전에 mark로 보류를 비우고, 한 묶음 안에서 같은 키는 마지막 값만 한 번 set** — 읽는 쪽이 서비스 값을 기준으로 삼는 구조는 그대로 둔다.
- 같은 서비스를 다시 읽는 검증은 **같은 앞의 값**을 읽으므로 이 문제를 못 잡는다 — `keys`의 st 3 잔존 여부를 보는 것이 확인 방법이다.
