# issue/messaging/mqpub-batch-key-dedupe — 정답

태그: `silent-failure` · `contract-drift` · `identity`

## 정답
<!-- 질문 1:1 대응 -->

1. **1건.** 두 키의 끝 12바이트가 모두 `345.20240801`이다.\
mqpub은 한 배치 안에서 키의 끝 12바이트가 같은 메시지를 중복으로 보고 **첫 메시지만** 스풀에 저장한다.\
나머지는 오류 없이 버리고, 출력의 `accepted`는 요청한 2를 그대로 찍는다.
   > **배치** — `mqpub publish` 한 번의 호출로 넣은 줄 전체. 배치 번호(`batch N`)가 1 증가한다.

2. **배치가 다르면 둘 다 남는다.** 비교는 같은 publish 호출 안에서만 일어난다.\
키가 12바이트보다 짧으면 키 전체가 비교 대상이다 — `abc`와 `abc`는 같고, `abc`와 `xabc`는 다르다.\
즉 "끝 12바이트(짧으면 전체)가 완전히 같다"가 판정 기준이다.

3. **성공 신호가 전부 정상이기 때문이다.** exit 0, stderr 없음, `accepted`=요청 건수.\
발행 측은 "보냈다"고 기록하고, 손실은 소비자 쪽 "받지 못함"으로만 드러난다.\
정산 완료 웹훅 사건에서도 발행 로그는 매일 전량 성공이었고, 일부 가맹점의 미수신 문의로 처음 드러났다.\
단서는 `mqpub stat -t <토픽>`의 messages 증가분이 accepted 합계보다 작다는 것 하나였다.

4. **업무 식별자의 대부분이 비교 범위 밖으로 밀린다.** 키 끝의 `.20240801`만 9바이트라 가맹점 번호의 끝 3자리까지만 비교에 들어간다.\
번호 끝 3자리가 같은 가맹점끼리는 같은 배치에서 첫 가맹점만 이벤트를 받았다.\
배치 구성(그날 정산이 끝난 가맹점 조합)이 매일 달라서, 손실 대상도 매일 달라 "무작위 유실"처럼 보였다.\
같은 가맹점이 다른 날에는 정상 수신하는 것도 이 때문이다 — 그날 배치에 끝자리가 같은 다른 가맹점이 먼저 있었느냐에 달려 있다.

5. **③만 모두 지킨다.**\
① 메시지마다 publish: 손실은 사라지지만 한 회차가 여러 배치로 갈라져 회차 단위 순서·원자성이 깨지고, 호출 수가 건수만큼 는다.\
② 난수 꼬리: 끝 12바이트는 구별되지만, 같은 이벤트를 재발행하면 키가 달라져 소비자의 "같은 키는 한 번만 처리" 중복 방지가 무력화된다.\
③ 결정적 해시 꼬리: `sha1(논리 키)`의 hex 12자를 `:` 뒤 맨 끝에 두면 메시지마다 끝 12바이트가 다르고, 같은 이벤트는 늘 같은 키다. 논리 키는 앞에 그대로 남아 사람이 읽을 수 있고, 네임스페이스로 시작하는 사내 키 규약도 그대로다. 키 길이 상한(64바이트) 안에 충분히 들어간다.\
업무 식별자를 키 끝으로 옮기는 방법은 식별자 끝자리가 겹치면(일련번호 끝이 같으면) 같은 문제가 재발해 선택하지 않았다.
   > **멱등 키** — 같은 사건이면 언제 만들어도 같은 값인 키. 소비자가 재전달을 걸러내는 근거가 된다.

6. **탐침 4~5회로 확정된다.**\
끝 12바이트가 같고 그 앞이 다른 키 두 줄을 한 배치로 publish → `consume`으로 1건만 남는지 본다.\
끝 11바이트만 같은 키 두 줄로 반복 → 2건 모두 남는다(경계가 12바이트임을 확인).\
같은 키를 두 번의 publish로 나눠 보냄 → 2건 모두 남는다(배치 범위 확인).\
매번 `stat`의 messages와 `accepted`를 대조한다.

7. **accepted가 아니라 저장된 것을 센다.** 발행 직후 `stat`의 messages 증가분이 보낸 건수와 같은지 대조하고, 다르면 회차를 실패로 기록한다.\
더 근본적으로는 키를 만드는 함수에 "배치 안에서 끝 12바이트가 유일한가"를 검사하는 단언을 두면, 규칙에 어긋나는 키 규약 변경을 배포 전에 잡는다.

## 문제 구조 (추상화 코드)

### 변형 A — 공통 꼬리 키가 배치 안에서 서로 덮임 (정산 완료 이벤트)
① 문제 코드
```ts
// 회차마다 정산이 끝난 가맹점 이벤트를 한 배치로 발행
const key = (e) => `settle.done.${e.merchantId}.${e.date}`;   // 끝 12바이트 = "345.20240801"
mq.publish(topic, events.map((e) => ({ key: key(e), payload: encode(e) })));
// → accepted = events.length, exit 0 — 실제 저장은 "끝자리 그룹"당 1건
```
② 고친 코드
```ts
import { createHash } from "crypto";
const logical = (e) => `settle.done.${e.merchantId}.${e.date}`;
const key = (e) => {
  const l = logical(e);
  return `${l}:${createHash("sha1").update(l).digest("hex").slice(0, 12)}`;   // 끝 12바이트가 메시지마다 다름, 결정적
};
const before = mq.stat(topic).messages;
mq.publish(topic, events.map((e) => ({ key: key(e), payload: encode(e) })));
if (mq.stat(topic).messages - before !== events.length) markRunFailed();     // 저장 건수 대조
```
무엇이 깨졌나: 키가 공통 꼬리(일자)로 끝나 업무 식별자의 끝 3자리만 비교 범위에 들어갔고, 벤더의 배치 내 중복 판정(끝 12바이트)에서 서로 같은 메시지로 취급됐다.\
검증 기록: 2024-08-02 — mqpub 2.6.x, 사건 기록 대조·추상화.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| 메시지별 publish | 회차 원자성 불필요 | 호출 수 = 건수 | 회차가 여러 배치로 갈라짐 | 건수가 적고 순서가 무관할 때 |
| 난수 꼬리 | 소비자 중복 방지 없음 | 낮음 | 재발행 시 중복 처리 | 재발행이 없는 일회성 이벤트 |
| 식별자를 끝으로 | 식별자 끝 12바이트가 유일 | 낮음 | 번호 체계 변경 시 재발 | 식별자가 길고 끝자리가 고유할 때 |
| 결정적 해시 꼬리 | 키 64바이트 상한 여유 | 해시 1회 | 없음(48비트 해시 충돌 무시 가능) | 기본값 |

결론: 회차 원자성과 소비자 중복 방지를 둘 다 써야 하는 사내 표준 환경에서는 결정적 해시 꼬리가 기본값이다.
