# issue/dbsnap/wal-retention-shorter-than-snapshot — 정답

태그: `silent-failure` · `contract-drift`

## 정답
<!-- 질문 1:1 대응 -->

1. **할 수 없다.** 목요일 14:00 복구는 일요일 스냅샷을 복원한 뒤 일요일~목요일 WAL을 순서대로 재생해야 한다.\
보존 3일이면 목요일에는 화~목 WAL만 남아 있고 일·월 WAL은 지워졌다. 재생은 첫 빠진 구간에서 멈춘다.
   > **WAL 아카이브** — 데이터베이스 변경 기록을 순서대로 보관한 것. 스냅샷 이후 시점으로 가려면 빠짐없이 재생해야 한다.

2. **두 작업이 각자 성공했기 때문이다.** 스냅샷 작업은 일요일마다 성공했고, WAL 아카이브·정리 작업도 매일 성공했다.\
어느 작업도 "가장 오래된 WAL이 최신 스냅샷보다 앞서는가"를 확인하지 않았다.\
분기 리허설에서 수요일 시점 복구를 시도하다 "WAL 세그먼트 없음"으로 실패해 드러났다.

3. **가장 최근 스냅샷의 시작 시각부터 지금까지의 WAL이 끊김 없이 남아 있어야 한다.**\
더 이전 시점까지 복구하려면 그 이전 스냅샷과 그 뒤 WAL도 함께 남아 있어야 한다. 즉 보존 기간 ≥ 스냅샷 주기 + 스냅샷 소요 시간이다.

4. **딱 7일은 부족하다.** 스냅샷이 몇 시간 걸리면 시작 시각 기준 WAL이 그만큼 더 필요하고, 스냅샷이 한 번 실패하면 다음 주까지 공백이 생긴다.\
이번에는 보존을 10일로 늘리고, 스냅샷 실패 시 WAL 정리를 멈추는 조건을 넣었다. 저장 비용 증가는 스냅샷 주기 변경으로 아낀 금액보다 작았다.

5. **백업 성공은 "파일이 만들어졌다"이고, 복구 가능은 "그 파일들로 원하는 시점에 도달할 수 있다"이다.**\
둘 사이에는 구성 요소 간 관계(스냅샷과 WAL의 연속성)·복원 절차·권한·버전 호환이 있다. 실제로 복원해 보기 전에는 확인되지 않는다.

6. **매일: "가장 오래된 WAL 시각 ≤ 최근 스냅샷 시작 시각"을 확인하고 어긋나면 경보한다.**\
**매주: 무작위 시점으로 자동 복구 리허설을 돌려 행 수·최근 거래 시각을 검증한다.**

## 문제 구조 (추상화 코드)

### 변형 A — 주기만 바꾸고 보존은 그대로
① 문제 코드
```yaml
snapshot:
  schedule: "0 2 * * 0"      # 매일 → 매주 일요일
wal_archive:
  retention_days: 3          # 그대로
```
② 고친 코드
```yaml
snapshot:
  schedule: "0 2 * * 0"
wal_archive:
  retention_days: 10         # 주기 7 + 소요 + 여유
  prune_requires_snapshot_success: true
```
무엇이 깨졌나: 서로 의존하는 두 설정 중 하나만 바꿨다.

### 변형 B — 연속성 감시
① 문제 코드
```sh
dbsnap last-status | grep -q SUCCESS || alert "snapshot failed"   # 작업 성공만 확인
```
② 고친 코드
```sh
snap_start=$(dbsnap last-snapshot --field start_epoch)
oldest_wal=$(dbsnap wal oldest --field epoch)
[ "$oldest_wal" -le "$snap_start" ] || alert "PITR gap: oldest WAL newer than snapshot start"
```
무엇이 깨졌나: 산출물 각각의 존재가 아니라 그 관계가 복구 조건이었다.
