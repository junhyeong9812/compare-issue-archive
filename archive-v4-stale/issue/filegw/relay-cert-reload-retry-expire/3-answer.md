# issue/filegw/relay-cert-reload-retry-expire — 정답

태그: `silent-failure` · `environment-drift` · `fail-closed`

## 정답
<!-- 질문 1:1 대응 -->

1. **받지 못한다.** `put`은 파일을 게이트웨이 스풀에 넣고 `queued`를 출력할 뿐이다.\
릴레이 워커가 파트너로 mTLS 연결을 열다가 인증서 만료로 핸드셰이크에 실패하면, 상태는 `Q` → `R`로 바뀌고 15분마다 재시도한다.\
`status`는 72시간 동안 `R`과 재시도 횟수(`try 12` 등)를 보여 주고, 72시간이 지나면 `X`가 된다.
   > **스풀 적재(`Q`)** — 게이트웨이 내부 디스크에 파일이 들어간 상태. 파트너 쪽에는 아무 일도 일어나지 않았다.

2. **릴레이 워커가 인증서를 기동 시점에만 읽기 때문이다.**\
새 인증서 파일은 키스토어 경로에 있었지만, 워커 프로세스는 두 달 전 기동 때 메모리에 올린 구 인증서를 계속 썼다.\
구 인증서가 만료되는 순간부터 핸드셰이크가 실패했다 — 교체 작업 자체는 "완료"로 처리돼 있었다.\
`filegw reload`(또는 워커 재기동)를 했어야 했다.

3. **첫 실패로부터 72시간 뒤 `X`가 된다.** 파일은 `spool/dead/<id>`로 옮겨지고 자동으로 다시 보내지지 않는다.\
인증서를 고친 뒤 `filegw requeue <id>`로 다시 넣어야 한다 — 같은 파일을 `put`으로 새로 넣으면 새 id가 생겨 대사 기록이 둘로 갈린다.\
이번 사건은 `R` 상태(72시간 이내)에서 발견돼 reload 직후 다음 재시도에서 `D`로 넘어갔고, 그 전 회차 2건은 이미 `X`라 requeue했다.

4. **`R`은 게이트웨이 입장에서 정상 경로이기 때문이다.**\
`R` 경보는 설정값 `alert_on_retry`(기본 off)로만 켜진다. `X` 경보는 켜져 있었지만 72시간 뒤에야 울린다.\
배치는 `queued`를 받으면 "전송 완료"로 기록했고, 이후 상태를 묻지 않았다.

5. **이름 조건 격리는 게이트웨이가 파일을 받아들인 직후 규칙으로 걸러내는 것이고, 이 사건은 전송 경로(TLS) 문제다.**\
먼저 `status`의 상태 문자를 본다 — `R`/`X`이면 연결·인증서 쪽, 그 밖의 보류 상태면 파일 자체(이름·내용) 쪽이다.\
`filegw tls-check <partner>`가 실패하면 인증서 문제로 확정된다.

6. **교체 절차**: 파일 교체 → `filegw reload` → `filegw tls-check <partner>` 성공 확인을 한 단계로 묶는다. 만료 30일 전 경보를 둔다.\
**배치 완료 판정**: `put` 뒤 `status`가 `D`가 될 때까지(제한 시간 안에서) 확인하고, `R`이 일정 횟수를 넘으면 실패로 올린다. `alert_on_retry`를 켠다.

## 문제 구조 (추상화 코드)

### 변형 A — 적재 응답을 전달 완료로 기록함 (정산 파일 배치)
① 문제 코드
```python
out = run(["filegw", "put", "--partner", partner, path])   # "queued F000..."
job.mark_sent(parse_id(out))                                # 전달 확인 없음
```
② 고친 코드
```python
fid = parse_id(run(["filegw", "put", "--partner", partner, path]))
st = wait_status(fid, until={"D", "X"}, timeout=timedelta(hours=2))
if st != "D":
    raise TransferNotDelivered(fid, st)                     # R 장기화도 실패로 올린다
job.mark_sent(fid)
```
무엇이 깨졌나: 비동기 전달 시스템의 접수 응답을 최종 결과로 썼다 — 실패는 재시도 상태에 숨어 72시간 동안 보이지 않았다.

### 변형 B — 인증서 파일만 교체하고 프로세스에 반영하지 않음 (인증서 갱신 작업)
① 문제 코드
```sh
cp new-client.p12 /etc/filegw/keystore/HNB.p12   # 파일만 교체
# 작업 완료 처리
```
② 고친 코드
```sh
cp new-client.p12 /etc/filegw/keystore/HNB.p12
filegw reload
filegw tls-check HNB || exit 1                     # 실제 핸드셰이크로 확인
```
무엇이 깨졌나: 설정 파일과 실행 중 프로세스의 상태가 달랐다 — 교체 확인을 파일 존재로 했다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| 배치가 `D`까지 폴링 | status 조회 권한 | 배치 시간 증가 | 파트너가 느리면 타임아웃 오탐 | 마감 시각이 있는 정산 파일 |
| `alert_on_retry` 켜기 | 운영 경보 채널 | 작음 | 일시 장애에도 경보(소음) | 모든 파트너 — 기본 |
| 인증서 만료 30일 전 경보 | 만료일 수집 | 작음 | reload 누락은 못 잡음 | 교체 절차와 함께 |

**결론**: 경보와 만료 감시는 원인 쪽 안전망이고, 배치의 `D` 확인은 결과 쪽 안전망이다. 정산 파일처럼 마감이 있는 전송은 둘 다 둔다.
