# issue/ordhub/live-commerce-hot-partition-lag — 정답

태그: `latency` · `partitioning` · `capacity`

## 정답
<!-- 질문 1:1 대응 -->

1. **한 가맹점 주문이 전부 파티션 하나로 가서 그 파티션의 소비자 하나가 상한이었다.**

2. **가맹점 안 주문 처리 순서를 보장하려고 했다.**\
실제 업무 규칙은 주문 단위 상태 순서만 필요했다.

3. **다른 가맹점은 다른 파티션이라 지연이 없었다.**

4. **재고 차감이 늦어 한정 수량 상품이 140건 초과 판매됐다.**\
판매자와 협의해 취소·보상했다.

5. **파티션 키를 주문 ID로, 파티션별 소비 지연 경보(1분), 한정 수량 상품은 주문 시 동기 재고 차감.**

## 문제 구조 (추상화 코드)

### 변형 A — 순서 보장 범위를 필요 이상으로 넓힌 파티션 키
① 문제 코드
```java
producer.send(new Record("orders", order.merchantId(), event));
```
② 고친 코드
```java
producer.send(new Record("orders", order.orderId(), event));   // 주문 단위 순서만 보장
```
무엇이 깨졌나: 필요한 순서 범위(주문)보다 넓은 범위(가맹점)를 키로 잡아 부하 분산을 잃었다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| 주문 ID 키 | 가맹점 단위 순서 불필요 | 작음 | 가맹점 단위 집계 소비자 수정 | 기본 |
| 대형 가맹점 키 분할(접미 번호) | 가맹점 목록 관리 | 중간 | 목록 누락 | 대안 |
| 파티션 수 증설 | — | 작음 | 한 가맹점 몰림은 그대로 | 선택하지 않은 방법 |

**결론**: 파티션 키는 필요한 순서 범위만큼만 좁힌다.
