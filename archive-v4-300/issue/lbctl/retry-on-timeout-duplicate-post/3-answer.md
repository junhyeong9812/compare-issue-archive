# issue/lbctl/retry-on-timeout-duplicate-post — 정답

태그: `duplicate` · `config`

## 정답
<!-- 질문 1:1 대응 -->

1. **백엔드 B가 같은 지급을 다시 수행한다.** A도 7초 뒤 완료해 두 번 송금됐다.

2. **월말 은행 펌뱅킹 응답이 평소 1초에서 6~9초로 늘었기 때문이다.**

3. **두 번째 요청은 같은 결과를 받고 송금하지 않았을 것이다.** 이번 API는 멱등 키가 없었다.

4. **GET 라우트와 연결 실패(connect-failure)에만.** 쓰기 라우트는 재시도를 끄고 클라이언트가 멱등 키로 재시도한다.

## 문제 구조 (추상화 코드)

### 변형 A — 쓰기 라우트에 타임아웃 재시도
① 문제 코드
```yaml
route: /payouts
retry: { retry_on: [timeout, 5xx], per_try_timeout: 5s, retries: 1 }
```
② 고친 코드
```yaml
route: /payouts
retry: { retry_on: [connect-failure], retries: 1 }
timeout: 30s
# 앱: Idempotency-Key 필수, (key) UNIQUE
```
무엇이 깨졌나: 인프라 계층의 재시도가 업무 의미(송금 1회)를 몰랐다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| 쓰기 라우트 재시도 제한 | lbctl 설정 | 작음 | 일시 오류가 사용자에게 노출 | 기본 |
| 멱등 키 | API 계약 변경 | 중간 | 클라이언트 미적용 | 함께 |
| 타임아웃 연장만 | 없음 | 작음 | 더 느리면 재발 | 선택하지 않은 방법 |

**결론**: 재시도는 멱등성이 보장되는 곳에서만 한다. 중복 9건은 은행 반환 요청으로 회수했다.
