# issue/stockpush/upgrade-glibc-requirement-rollback — 정답

태그: `deployment` · `environment-drift` · `rollback`

## 정답
<!-- 질문 1:1 대응 -->

1. **동적 로더가 요구 버전의 라이브러리를 찾지 못한다는 오류였다.**\
프로그램 코드가 시작되기 전 단계에서 끝났다.

2. **스테이징 서버는 지난해 OS를 올려 라이브러리가 새 버전이었다.**\
운영 배치 서버는 같은 작업이 미뤄져 있었다.

3. **이전 패키지가 사내 저장소 보관 정책(최신 1판)으로 삭제돼 벤더에 재요청했다.**\
그 사이 재고 연동이 멈췄다.

4. **환경 일치, 이전 두 판 보관, 업그레이드 전 운영과 같은 OS 컨테이너에서 실행 확인.**

## 문제 구조 (추상화 코드)

### 변형 A — 운영과 다른 환경에서만 사전 검증
① 문제 코드
```sh
# 스테이징에서 확인 후 운영 적용
ssh staging 'stockpush --version'
```
② 고친 코드
```sh
# 운영과 같은 OS 이미지에서 실행 확인
docker run --rm -v $PWD/pkg:/pkg legacy-os:prod /pkg/stockpush --version
```
무엇이 깨졌나: 검증 환경이 운영과 달라 "스테이징 통과"가 아무것도 보장하지 못했다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| 운영 OS 이미지로 사전 실행 | 운영 이미지 보유 | 작음 | 이미지 낡음 | 기본 |
| 이전 두 판 보관 | 저장소 정책 수정 | 작음 | 용량 | 기본 |
| 운영 서버 OS 업그레이드 | 변경 창 | 큼 | 다른 배치 영향 | 장기 |

**결론**: 업그레이드 검증은 운영과 같은 환경에서, 롤백 경로는 업그레이드 전에 확보한다.
