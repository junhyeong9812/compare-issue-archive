# issue/amlscan/rule-window-unit — 정답

태그: `contract-drift` · `silent-failure`

## 정답
<!-- 질문 1:1 대응 -->

1. **60초 안에 5회로 해석한다.** 실제 분할송금은 수 분 간격이라 걸리지 않는다.

2. **합성 데이터가 거래를 수 초 간격으로 몰아 넣었기 때문이다.** 실제 운영 데이터 리플레이는 하지 않았다.

3. **`window: 60m` 또는 `3600s`로 쓴다.** 엔진 4.3부터 단위 없는 값에 경고를 내는 옵션(`strict_units`)이 있다 — 켰다.

4. **새 룰은 원래 경보가 적을 수 있다고 여겼기 때문이다.** 기대 경보 수를 정해 두지 않아 0건이 정상처럼 보였다. 2주 뒤 수동 조사에서 같은 패턴 고객 6명이 발견됐다.

5. **운영 데이터 리플레이 + 기대 범위.** 지난 30일 데이터로 돌려 경보 수가 기대 범위(이번엔 20~60건)에 드는지 본다. 0건이면 배포하지 않는다.

## 문제 구조 (추상화 코드)

### 변형 A — 단위 없는 창
① 문제 코드
```yaml
rule: split-xfer-01
window: 60
count: 5
sum: 9000000
```
② 고친 코드
```yaml
rule: split-xfer-01
window: 60m            # 단위 명시
count: 5
sum: 9000000
expect_alerts_30d: [20, 60]   # 배포 전 리플레이 범위
```
무엇이 깨졌나: 단위 없는 숫자를 작성자와 엔진이 서로 다른 단위로 읽었고, 압축된 시험 데이터가 그 차이를 가렸다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| 단위 명시 + strict_units | 엔진 4.3+ | 작음 | 구 룰 정리 필요 | 기본 |
| 운영 리플레이 기대 범위 | 30일 데이터 | 중간 | 범위 설정 주관 | 새 룰 전부 |
| 경보 0건 일일 감시 | 대시보드 | 작음 | 원래 드문 룰은 소음 | 보조 |

**결론**: 단위는 문법으로 강제하고, 룰의 효과는 운영 데이터로 확인한다.
