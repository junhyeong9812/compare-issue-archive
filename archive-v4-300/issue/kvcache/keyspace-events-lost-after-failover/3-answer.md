# issue/kvcache/keyspace-events-lost-after-failover — 정답

태그: `environment-drift` · `silent-failure`

## 정답
<!-- 질문 1:1 대응 -->

1. **오지 않는다.** 새 마스터는 기본값(꺼짐)이었다.

2. **구독은 정상이고 메시지만 없었기 때문이다.** 워커는 '이벤트 0건'을 이상으로 보지 않았다.

3. **키는 만료된다.** 하지만 DB의 `hold_qty`를 줄이는 처리는 이벤트에 달려 있어 그대로 남았다 — 판매 가능 수량이 줄어 품절로 보였다.

4. **DB에 홀드 만료 시각을 두고 1분 주기로 지난 홀드를 해제한다.** 이벤트는 빠른 경로로만 쓴다.

## 문제 구조 (추상화 코드)

### 변형 A — 만료 후처리를 키스페이스 이벤트에만 의존
① 문제 코드
```java
redis.subscribe("__keyevent@0__:expired", key -> stock.release(holdId(key)));
```
② 고친 코드
```java
@Scheduled(fixedDelay = 60_000)
void sweep() { holdRepo.findExpired(now()).forEach(h -> stock.release(h.id())); }
// 이벤트 구독은 남기되 release 는 멱등
```
무엇이 깨졌나: 전달 보장이 없는 신호를 정합성의 유일한 근거로 썼다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| 주기 스캔 정본 + 이벤트 보조 | 만료 시각 컬럼 | 작음 | 최대 1분 지연 | 기본 |
| 설정 템플릿에 notify 포함 | kvcache 템플릿 관리 | 작음 | 다른 설정 누락 | 함께 |
| 이벤트 0건 경보 | 메트릭 | 작음 | 한산한 시간 오탐 | 보조 |

**결론**: 정리 작업은 스캔으로 보장하고, 런타임 설정은 템플릿으로 모든 노드에 고정한다.
