# issue/pushq/run-cron-overlap-duplicate-send — 정답

태그: `concurrency` · `scheduling` · `idempotency`

## 정답
<!-- 질문 1:1 대응 -->

1. **그날만 1회 실행이 1분을 넘었다.**\
10시 정각 예약이 92만 건 몰려 실행이 4분 걸렸다.

2. **완료 표시가 발송 뒤에 있었다.**\
다음 실행이 같은 목록을 조회해 같은 대상을 다시 보냈다.

3. **10:00 ~ 10:06, 실행 시간이 1분을 넘던 구간뿐이었다.**

4. **flock으로 실행 하나만 허용, 대상은 조회 시 "처리 중"으로 선점, 실행 시간 50초 초과 경보.**

## 문제 구조 (추상화 코드)

### 변형 A — 잠금 없는 매분 크론
① 문제 코드
```sh
* * * * * /opt/push/run_send.sh
```
② 고친 코드
```sh
* * * * * flock -n /run/push_send.lock /opt/push/run_send.sh || echo "skip: running" | logger
```
무엇이 깨졌나: "1분 안에 끝난다"는 가정에 기대 겹침 방지가 없었다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| flock 실행 잠금 | 단일 호스트 | 작음 | 장시간 실행 시 다음 회차 지연 | 기본 |
| 조회 시 선점 표시 | 상태 컬럼 | 중간 | 선점 후 장애 시 회수 필요 | 기본 |
| 크론 주기 5분 | 지연 허용 | 작음 | 발송 정시성 저하 | 선택하지 않은 방법 |

**결론**: 주기 작업은 겹침을 전제로 설계한다 — 잠금과 선점을 둘 다 둔다.
