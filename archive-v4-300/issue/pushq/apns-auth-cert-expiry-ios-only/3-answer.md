# issue/pushq/apns-auth-cert-expiry-ios-only — 정답

태그: `credential` · `partial-failure` · `vendor-notice`

## 정답
<!-- 질문 1:1 대응 -->

1. **플랫폼별 자격증명부터 의심한다.**\
같은 캠페인에서 OS로만 갈리면 메시지·시각보다 iOS 발송 경로(APNs) 문제다.

2. **갱신한 인증서를 벤더 콘솔에 올리지 않았다.**\
갱신 절차서가 "애플 개발자 센터에서 재발급"까지만 적혀 있었다.

3. **자격증명은 실제 APNs로 보낼 때 쓰이기 때문이다.**\
예약 단계는 대상·시각만 받으므로 정상 응답을 줬다.

4. **벤더 발송 로그의 실패를 사내 지표로 가져오지 않았다.**\
예약 성공 건수만 대시보드에 있었다.

5. **OS·앱 버전별 수신 분포를 먼저 본다.**\
한 플랫폼에 몰리면 자격증명·연동, 고르게 흩어지면 예약 시각·대상 선정 쪽이다.

## 문제 구조 (추상화 코드)

### 변형 A — 예약 응답만 성공 지표로 사용
① 문제 코드
```python
ok = pushq_schedule(campaign)
metrics.incr("push.scheduled", ok.count)
```
② 고친 코드
```python
ok = pushq_schedule(campaign)
metrics.incr("push.scheduled", ok.count)
# 발송 시각 이후 벤더 발송 로그를 수집해 플랫폼별 실패율 기록
collect_delivery_log(campaign, by=["platform"], alert_if_fail_rate=0.05)
```
무엇이 깨졌나: 성공 지표가 예약 단계에서 멈춰 발송 단계의 플랫폼 실패를 보지 못했다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| 토큰 키(.p8) 전환 | 벤더가 토큰 키 지원 | 작음 | 키 파일 유출 | 기본 |
| 플랫폼별 발송 실패율 경보 | 발송 로그 수집 | 중간 | 로그 지연 | 기본 |
| 인증서 만료 대장 | 대장 관리 | 작음 | 대장 누락 | 토큰 키 전환 전까지 |

**결론**: 예약 성공은 발송 성공이 아니다 — 발송 로그를 플랫폼별로 본다.
