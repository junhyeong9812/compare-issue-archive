# issue/evstream/null-key-partition-reorder — 정답

태그: `ordering` · `data-semantics`

## 정답
<!-- 질문 1:1 대응 -->

1. **있다.** 두 이벤트가 다른 파티션에 들어가면 소비 순서는 보장되지 않는다.

2. **파티션 3의 리더 브로커가 디스크 지연으로 느렸다.** 그 파티션에 들어간 PAID가 다른 파티션의 PENDING보다 늦게 소비됐다.

3. **여전히 필요하다.** 생산자 재시도·다중 생산자에서 역전이 생길 수 있다 — 상태 버전 비교는 값싼 보험이다.

4. **같은 주문 이벤트들의 파티션 번호를 본다.** 서로 다르면 이 사건이다.

## 문제 구조 (추상화 코드)

### 변형 A — 키 없는 발행
① 문제 코드
```java
producer.send(new Record<>("order.status", null, event));
```
② 고친 코드
```java
producer.send(new Record<>("order.status", event.orderId(), event));   // 같은 주문 = 같은 파티션
// 소비자
if (event.seq() <= view.seqOf(event.orderId())) return;               // 옛 이벤트 무시
```
무엇이 깨졌나: 순서가 필요한 이벤트에 파티션 키를 주지 않았다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| 주문 id 키 | 키 분포 고름 | 작음 | 핫 키 | 기본 |
| 소비자 seq 비교 | 생산자 seq 부여 | 작음 | seq 누락 | 함께 적용 |

**결론**: 순서가 의미 있는 이벤트는 엔터티 id를 키로 두고, 소비자는 버전으로 방어한다.
