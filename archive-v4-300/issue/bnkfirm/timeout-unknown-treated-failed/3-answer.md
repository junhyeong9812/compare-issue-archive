# issue/bnkfirm/timeout-unknown-treated-failed — 정답

태그: `idempotency` · `async-status`

## 정답
<!-- 질문 1:1 대응 -->

1. **T1·T2가 둘 다 이체된다.** 은행은 고유번호가 다르면 다른 이체로 본다.

2. **연초 지급 피크로 전용선 지연이 늘었다.** 평균 응답이 2초에서 9초로 늘어 10초 타임아웃에 걸리기 시작했다.

3. **'이미 처리됨' 응답과 원 결과를 돌려준다.** 그래서 같은 번호 재전송은 안전하다.

4. **은행 거래내역의 전문 고유번호와 사내 이체 기록을 1:1로 맞춘다.** 사내에 실패로 남은 번호가 은행에 있으면 이 유형이다.

## 문제 구조 (추상화 코드)

① 문제 코드
```java
try { firm.transfer(newSeq(), req); } catch (Timeout e) { req.setFailed(); }
```
② 고친 코드
```java
String seq = req.seqOrAssign();
try { firm.transfer(seq, req); }
catch (Timeout e) { req.setUnknown(); }      // 조회 배치가 inquire(seq) 로 확정
```
무엇이 깨졌나: 결과를 모르는 상태를 실패로 단정하고, 재시도에서 멱등 키를 바꿨다.

## 방안 비교

| 방안 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|
| UNKNOWN + 결과 조회 + 같은 번호 재전송 | 중간 | 조회 지연 | 기본 |
| 타임아웃 연장 | 작음 | 지연 시 같은 문제 | 보조 |

**결론**: 타임아웃은 조회로 확정하고, 재시도는 같은 고유번호로 한다.
