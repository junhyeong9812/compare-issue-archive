# issue/outboxd/dead-tuple-bloat-poll-slow — 정답

태그: `performance` · `database`

## 정답
<!-- 질문 1:1 대응 -->

1. **죽은 튜플이 수억 개 쌓인다.** 폴링이 매번 그 위를 훑는다.

2. **열린 트랜잭션보다 새로운 죽은 튜플은 정리할 수 없다.** 6시간짜리 분석 쿼리가 정리를 막았다.

3. **파티션 관리 작업이 필요하다.** 대신 삭제가 메타데이터 작업이라 죽은 튜플이 남지 않는다.

## 문제 구조 (추상화 코드)

### 변형 A — 고빈도 삭제 테이블에 기본 vacuum 설정
① 문제 코드
```sql
DELETE FROM outbox WHERE id = ANY(:published_ids);
```
② 고친 코드
```sql
ALTER TABLE outbox SET (autovacuum_vacuum_scale_factor = 0.01, autovacuum_vacuum_cost_limit = 2000);
-- 장기: outbox 를 일 단위 파티션으로, 3일 지난 파티션 DROP
```
무엇이 깨졌나: 대량 삭제 큐 테이블을 일반 테이블 설정으로 운영했다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| vacuum 임계 조정 | 테이블 설정 | 작음 | I/O 증가 | 기본 |
| 시간 파티션 + DROP | 파티션 관리 | 중간 | 관리 누락 | 함께 적용 |
| 분석 쿼리 복제본 분리 | 복제본 | 중간 | 복제 지연 | 함께 적용 |

**결론**: 큐처럼 쓰는 테이블은 vacuum 설정을 따로 두고, 가능하면 파티션 단위로 지운다.
