# issue/ptsctl/earn-member-leading-zero — 정답

태그: `silent-failure` · `identity` · `parser-differential`

## 정답
<!-- 질문 1:1 대응 -->

1. **적립 번호(`P…`)와 exit 0이 나온다.** stderr는 비어 있다.\
그런데 `bal 000873`은 `000873 0`이고, `bal 873`이 `873 500`이다 — 포인트가 앞자리 0을 뗀 계정에 들어갔다.\
`873`이 다른 회원이면 그 회원 잔액이 늘고, 아무도 아니면 주인 없는 계정이 새로 생긴다.
   > **계정 키** — 벤더 원장이 포인트를 쌓는 단위. earn은 회원번호를 해석해 키를 만들고, 조회는 받은 글자를 그대로 키로 쓴다.

2. **숫자로만 된 번호만 수로 읽힌다.** `0A12`처럼 숫자 아닌 문자가 섞이면 그대로 `0A12`에 적립된다.\
`000000`은 `0` 계정으로 간다.\
`@000873`은 `@`를 떼고 `000873` 그대로 적립한다 — help에는 "@MBR is also accepted"뿐이라 같은 뜻처럼 읽히지만, 글자 그대로 적립하는 것은 이 표기뿐이다.\
`bal`·`hist`는 어느 경우든 받은 글자 그대로 찾는다(`@`만 뗀다).

3. **적립과 조회의 회원번호 해석이 달랐다.** 이관 배치는 회원번호를 그대로 `--mbr`에 넣었다.\
매장 카드 출신 회원은 카드에 찍힌 6자리(앞 0 포함)라 0을 뗀 번호로 적립됐고, 그 번호가 앱 회원 번호와 겹치면 앱 회원이 이관분을 받았다.\
앱 가입 회원 번호는 0으로 시작하지 않아 늘 맞았다.\
배치는 적립 번호를 받으면 "이관 완료"로 표시했으므로 오류가 없었고, 회원 문의("캐시백이 사라졌다")로 발견됐다.

4. **다른 사람의 번호가 된다.** 앞 0을 떼면 벤더가 하는 것과 같은 잘못을 호출부가 먼저 하는 것이고, 고정 자릿수로 0을 채우면 `873`(실제 앱 회원)이 `000873`(다른 회원)이 된다.\
회원번호는 발급된 문자열 그대로 다루고, 벤더에는 `@` 표기로 넘긴다.
   > **식별 문자열** — 산술 의미가 없는 번호. 수 타입으로 바꾸는 순간 앞 0·자릿수 정보가 사라져 다른 식별자와 충돌한다.

5. **바로잡을 수 없다.** earn은 양수 포인트만 받고, 같은 참조(REF)는 원장에 한 번만 허용된다(E19).\
잘못 쌓인 포인트 회수는 벤더·운영 조정으로 하고, 본인 계정 재적립은 새 참조로 `@` 표기를 써서 한다.\
재처리 전에 0을 뗀 번호의 `hist`로 어떤 참조가 잘못 들어갔는지 먼저 뽑아 둔다.

6. **회원번호별 조회로 판정한다.** 적립 번호는 원장에 기록됐다는 뜻일 뿐, 어느 계정인지는 말해 주지 않는다.\
보낸 회원번호 그대로 `bal`/`hist`를 조회해 보낸 참조와 포인트가 그 원장에 있는지 대사한다.\
근본 대처는 `@` 표기로 잘못된 적립 자체를 막는 것이고, 대사는 다른 경로에서 같은 일이 생길 때를 위한 안전망이다.

## 문제 구조 (추상화 코드)

### 변형 A — 회원번호를 그대로 넘긴 적립 (캐시백 이관)
① 문제 코드
```java
for (Migration m : batch)
    m.entryNo = pts.run("earn", "--mbr", m.memberNo, "--pt", m.points, "--ref", m.ref);  // "000873" → 계정 "873"
// exit 0, 적립 번호 수령 → 이관 완료로 표시
```
② 고친 코드
```java
for (Migration m : batch)
    m.entryNo = pts.run("earn", "--mbr", "@" + m.memberNo, "--pt", m.points, "--ref", m.ref);  // 글자 그대로
```
무엇이 깨졌나: 벤더 earn은 숫자뿐인 번호를 수로 읽는데, 호출부가 식별 문자열을 표기 없이 넘겼다.

### 변형 B — 호출부가 회원번호를 수 타입으로 보관 (선택하지 않은 우회의 원형)
① 문제 코드
```java
long memberNo = Long.parseLong(row.get("member"));   // 앞 0이 저장 단계에서 사라짐
pts.run("earn", "--mbr", String.valueOf(memberNo), ...);
```
② 고친 코드
```java
String memberNo = row.get("member");                  // 발급 문자열 그대로 보관
pts.run("earn", "--mbr", "@" + memberNo, ...);
```
무엇이 깨졌나: 식별자를 수로 보관해 벤더와 같은 정보 손실을 호출부가 먼저 냈다.

### 변형 C — 적립 번호로 완료를 판정함 (대사 누락)
① 문제 코드
```java
if (entryNo.startsWith("P")) m.markDone();            // 어느 계정에 쌓였는지 모름
```
② 고친 코드
```java
pts.run("earn", "--mbr", "@" + m.memberNo, ...);
if (!pts.history(m.memberNo).refs().contains(m.ref)) alert("not on own account: " + m.memberNo + " " + m.ref);
```
무엇이 깨졌나: 벤더 성공 신호를 실제 적립 위치 확인 대신 썼다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| earn에 `@` 표기 | 규칙(숫자뿐 → 수로 해석)을 안다 | 작음 | 표기 빠뜨린 다른 호출부 | 모든 earn 호출부 — 기본 |
| 0으로 시작하는 번호만 `@` | 같은 전제 | 작음 | 규칙이 바뀌면 분기 기준이 틀림 | 동작은 같으나 선택하지 않은 방법 |
| 회원번호를 0 없는 체계로 재발급 | 전 회원 번호 이관 | 매우 큼 | 카드 재발급·외부 연동 깨짐 | 선택하지 않은 방법 |
| 회원번호별 bal/hist 사후 대사 | 조회 권한 | 중간(호출 수) | 잘못된 적립 자체는 막지 못함 | `@` 표기와 함께 안전망 |

**결론**: 모든 earn 호출에 `@` 표기를 쓰는 것이 근본 대처이고, 회원번호별 조회 대사는 같은 종류의 오적립을 잡는 안전망이다.
