# issue/sharefs/nfs-nolock-concurrent-batch — 정답

태그: `concurrency` · `duplicate`

## 정답
<!-- 질문 1:1 대응 -->

1. **둘 다 잠금을 얻고 동시에 실행된다.**

2. **같은 노드의 잠금은 커널 로컬 잠금으로 서로 막는다.**

3. **노드 간 잠금이 동작한다.** 다만 클라이언트가 죽으면 리스 만료(90초)까지 잠금이 남는다.

4. **DB `job_lock` 행에 `SELECT ... FOR UPDATE NOWAIT`.** 파일 이름도 배치 실행 ID로 고정해 이중 생성이 덮어쓰게 했다.

## 문제 구조 (추상화 코드)

### 변형 A — 공유 스토리지 파일 잠금에 의존
① 문제 코드
```sh
flock -n /mnt/share/settle.lock ./settle.sh || exit 0
```
② 고친 코드
```sh
psql -c "SELECT 1 FROM job_lock WHERE name='settle' FOR UPDATE NOWAIT" ... # 트랜잭션 안에서 settle 실행
# 또는 스케줄러에서 동시 실행 금지 + 단일 인스턴스
```
무엇이 깨졌나: 파일 잠금의 범위가 마운트 옵션에 달려 있다는 점을 몰랐다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| DB 행 잠금 | DB | 작음 | DB 장애 시 미실행 | 기본 |
| 스케줄러 단일 실행 | 스케줄러 기능 | 작음 | 스케줄러 이중화 시 문제 | 함께 |
| NFS v4 전환 | 스토리지 작업 | 중간 | 리스 지연 | 보조 |

**결론**: 단일 실행은 스토리지가 아니라 DB나 스케줄러로 보장한다.
