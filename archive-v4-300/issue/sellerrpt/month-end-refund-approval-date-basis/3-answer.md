# issue/sellerrpt/month-end-refund-approval-date-basis — 정답

태그: `data-semantics` · `reconciliation` · `cutoff`

## 정답
<!-- 질문 1:1 대응 -->

1. **3월 31일 밤에 요청돼 4월 1일 새벽 승인된 환불이다.**

2. **리포트는 환불 요청일, PG는 승인일로 월을 정했다.**\
야간 일괄 승인 때문에 월말 요청분이 다음 달 승인이 된다.

3. **4월에는 반대로 PG 쪽 환불이 그만큼 많아진다.**\
두 달 합계는 맞는다.

4. **평소 차이는 수십만 원이라 오차로 처리됐다.**\
3월 행사 반품이 월말에 몰려 처음 크게 보였다.

5. **건 단위로 대사해 차이 건이 "다른 달에 있는지"부터 본다.**\
다음 달에 같은 환불이 있으면 기준일 이월, 어느 달에도 없으면 누락이다.

## 문제 구조 (추상화 코드)

### 변형 A — 시스템마다 다른 기준일
① 문제 코드
```sql
SELECT seller_id, SUM(amount) FROM refunds
WHERE requested_at >= '2025-03-01' AND requested_at < '2025-04-01' GROUP BY seller_id;
```
② 고친 코드
```sql
SELECT seller_id, SUM(amount) FROM refunds
WHERE pg_approved_at >= '2025-03-01' AND pg_approved_at < '2025-04-01' GROUP BY seller_id;
-- 승인 대기분은 별도 줄로 표시
```
무엇이 깨졌나: 같은 사건을 시스템마다 다른 날짜로 귀속해 월 단위 대사가 구조적으로 어긋났다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| 승인일 기준 통일 | PG 승인일 수집 | 작음 | 승인 지연 건 표시 필요 | 기본 |
| 리포트에 이월 항목 | 화면 수정 | 작음 | 판매자 혼란 | 병행 |
| 차이를 오차로 허용 | — | 없음 | 큰 달에 신뢰 상실 | 선택하지 않은 방법 |

**결론**: 월 귀속 기준일은 정산 원천(PG)과 같게 맞춘다.
