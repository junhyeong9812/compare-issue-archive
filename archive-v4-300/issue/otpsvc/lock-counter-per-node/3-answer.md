# issue/otpsvc/lock-counter-per-node — 정답

태그: `security` · `distributed-state`

## 정답
<!-- 질문 1:1 대응 -->

1. **최대 20회.** 노드 4대에 고르게 나뉘면 각 노드가 5회까지 받는다.

2. **시험 환경이 1대였다.**

3. **그 노드의 카운터가 0이 된다.** 배포 중에는 더 많이 시도할 수 있었다.

4. **발급 번호 하나를 맞힐 확률이 시도 횟수에 비례하기 때문이다.** 계정 다수를 대상으로 하면 의미 있는 성공 수가 나온다.

5. **캐시 클러스터에 `otp-fail:<요청ID>` 원자 증가 + 만료 3분.** 사용자 단위 일일 한도도 함께 둔다.

## 문제 구조 (추상화 코드)

### 변형 A — 노드 메모리 카운터
① 문제 코드
```java
int n = failures.merge(reqId, 1, Integer::sum);   // ConcurrentHashMap, 노드 로컬
if (n >= 5) lock(reqId);
```
② 고친 코드
```java
long n = cache.incr("otp-fail:" + reqId, Duration.ofMinutes(3));  // 공유, 원자
if (n >= 5) lock(reqId);
```
무엇이 깨졌나: 보안 한도를 수평 확장된 서버의 로컬 상태로 세어, 한도가 서버 수에 따라 바뀌었다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| 공유 캐시 카운터 | 캐시 클러스터 | 작음 | 캐시 장애 시 정책 | 기본 |
| LB 고정 세션 | LB 설정 | 작음 | 공격자가 세션 바꿈 | 선택하지 않은 방법 |
| DB 카운터 | DB 쓰기 | 중간 | 부하 | 캐시 없을 때 |

**결론**: 보안 카운터는 공유 저장소에서 원자적으로 센다. 캐시 장애 시에는 인증을 막는 쪽으로 둔다.
