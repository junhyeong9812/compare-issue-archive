# issue/cfgsvc/set-hidden-until-mark — 정리 (힌트)

태그: `silent-failure` · `contract-drift` · `single-source-of-truth`

## 전체 흐름

```
호출부 ──set KEY V──▶ cfgsvc ──▶ journal (변경 번호 C…, exit 0, stderr 없음)
                         │
   KEY 가 마지막 mark 때 값이 있었다 │ get KEY → 마지막 mark 때의 값 (이전 값)    keys: st 3
   KEY 가 처음 만드는 키다          │ get KEY → 방금 set한 값 (바로 보임)      keys: st 3
                         │
              cfgsvc mark ──▶ 그때까지의 변경이 get 에 보인다 → keys: st 0, 마크 번호 +1
              (변경이 없으면 같은 마크 번호만 다시 출력 — 부작용 없음)

  운영 콘솔                         야간 정산 배치
  set → get(이전 값) → "반영 실패"     ... → mark (스냅샷 번호 기록용) → 이때 비로소 보임
  (새 가맹점 = 새 키 → 바로 보여 "성공")

잘못된 교정: 콘솔이 자기가 set한 값을 화면에 표시 → 화면만 맞고, get 으로 읽는 결제 서버는 여전히 이전 값
올바른 교정: set 묶음을 다 한 뒤, get 으로 읽기 전에 mark 를 한 번 부른다
발견 방법:   keys 의 st (3 = 아직 안 보임, 0 = 보임) · set 직후 get 이 이전 값인지 직접 확인
```

## 핵심 문장

- `cfgsvc set`은 언제나 exit 0·변경 번호를 주지만, **이미 값이 있던 키는 다음 `mark` 전까지 `get`이 이전 값**을 준다.
- **처음 만드는 키는 set 직후 바로 보인다** — 신규 등록·첫 구축은 정상이고, 기존 값 변경만 조용히 늦는다.
- `mark`는 도움말에 "현재 마크 출력"으로만 적혀 있지만, 부르면 **그때까지의 변경을 get에 보이게** 만든다. 변경이 없으면 번호만 다시 출력한다.
- 대처: **set을 모두 한 뒤, 같은 서비스에서 값을 읽어 쓰기 전에 mark** — 읽는 쪽이 서비스 값을 기준으로 삼는 구조는 그대로 둔다.
- 같은 서비스를 다시 읽는 검증은 **같은 이전 값**을 읽으므로 이 문제를 못 잡는다 — `keys`의 st 3 잔존 여부를 보는 것이 확인 방법이다.
