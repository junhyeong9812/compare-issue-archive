# issue/kycflow/vendor-retry-double-billing — 정답

태그: `idempotency` · `data-semantics`

## 정답
<!-- 질문 1:1 대응 -->

1. **2건이다.** 첫 요청은 벤더에서 끝까지 처리돼 과금됐고, 재시도는 새 요청으로 다시 과금됐다.

2. **내부는 최종 성공 응답만 셌기 때문이다.** 타임아웃 난 첫 요청은 '실패'로 버려졌다.

3. **같은 키로 들어온 요청은 첫 처리 결과를 돌려주고 과금하지 않는다(24시간 보관).** 키는 `case_id:attempt_no`로 만든다 — 사람이 재심사를 누르면 attempt_no가 오른다.

4. **월말 가입 몰림 때 벤더 응답 p95가 3초를 넘었다.** 9월 마지막 주 차이가 5.1%로 가장 컸다.

5. **벤더 거래 ID 단위.** 벤더 청구 상세(거래 ID·요청 시각)와 내부 호출 로그를 붙이면 '한 심사 건에 벤더 거래 2건' 패턴이 바로 보인다.

## 문제 구조 (추상화 코드)

### 변형 A — 재시도마다 새 요청
① 문제 코드
```java
for (int i = 0; i < 3; i++) {
    try { return vendor.verify(req); }          // 헤더 없음
    catch (TimeoutException e) { /* 재시도 */ }
}
```
② 고친 코드
```java
String key = req.caseId() + ":" + req.attemptNo();
for (int i = 0; i < 3; i++) {
    try { return vendor.verify(req, Map.of("Idempotency-Key", key)); }
    catch (TimeoutException e) { /* 같은 키로 재시도 */ }
}
```
무엇이 깨졌나: 클라이언트의 '실패'가 서버에서는 '처리 완료'였다 — 재시도가 같은 일임을 서버에 알리지 않았다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| 멱등 키 전송 | 벤더 지원 | 작음 | 키 생성 실수 | 기본 |
| 타임아웃 6초로 연장 | UX 허용 | 작음 | 지연 체감 | 보조 |
| 거래 ID 단위 월 대사 | 청구 상세 수령 | 중간 | 사후 | 안전망 |

**결론**: 재시도는 멱등 키와 한 쌍이다. 과금 대사는 벤더 거래 ID 기준으로 한다.
