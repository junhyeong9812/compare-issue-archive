# issue/shiptrack/carrier-api-daily-quota-polling — 정답

태그: `resource-bounding` · `cost` · `integration`

## 정답
<!-- 질문 1:1 대응 -->

1. **호출 한도 초과(429)였다.**

2. **실시간 배송 알림을 위해 상태 변경을 빨리 알아야 해서 30분 → 5분으로 줄였다.**

3. **택배사 한도가 매일 0시 초기화된다.**

4. **택배사 웹훅으로 전환, 보조 폴링 2시간, 사용량 70% 경보, 조회 실패는 "잠시 후 다시" 표시.**

## 문제 구조 (추상화 코드)

### 변형 A — 신선도를 폴링 빈도로만 해결
① 문제 코드
```yaml
poll_interval: 5m       # 진행 중 운송장 전체
```
② 고친 코드
```yaml
webhook: enabled        # 상태 변경 즉시 수신
poll_interval: 2h       # 웹훅 누락 대비
quota_alert: 0.7
```
무엇이 깨졌나: 외부 호출 한도를 계산하지 않고 주기만 줄였다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| 웹훅 전환 | 택배사 지원 | 중간 | 웹훅 누락 | 기본 |
| 사용량 경보 | 사용량 집계 | 작음 | 대응 지연 | 기본 |
| 한도 상향 계약 | 비용 | 협의 | 비용 증가 | 선택하지 않은 방법 |

**결론**: 외부 조회 주기는 한도에서 거꾸로 계산하고, 가능하면 푸시를 받는다.
