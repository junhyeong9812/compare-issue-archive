# issue/ledgerctl/ha-failover-double-batch-run — 정답

태그: `concurrency` · `idempotency` · `deployment`

## 정답
<!-- 질문 1:1 대응 -->

1. **배치가 두 번 실행됐는지부터 의심한다.**\
차액이 정확히 하루치 배치 금액이면 부분 오류보다 이중 실행 가능성이 높다. 크론 로그에 두 노드의 실행 기록이 모두 있었다.

2. **이중화 리허설 후 옛 active 노드의 크론 데몬을 끄는 단계가 빠졌다.**\
리허설 절차서의 마지막 단계가 "원복" 섹션에만 있었다.

3. **정산 전표 배치는 공통 잠금 래퍼를 썼고, 환불 전표 배치는 쓰지 않았다.**\
5월에 새로 만든 배치라 템플릿 대신 직접 크론에 등록됐다.

4. **체크리스트가 "새 active 승격 확인"으로 끝났기 때문이다.**\
옛 노드에서 크론이 멈췄는지 보는 항목이 없었다. 이후 "양 노드 크론 상태 확인"을 추가했다.

5. **① 공통 잠금 래퍼를 모든 배치의 기본 템플릿으로 강제**\
**② 전표 메모 대신 사내 대사 테이블에 배치 회차 키를 남겨 같은 회차 두 번 기장을 대사에서 바로 찾기.** 이중 기장분은 역분개로 정리했다.

## 문제 구조 (추상화 코드)

### 변형 A — 잠금 없는 배치를 크론에 직접 등록
① 문제 코드
```sh
30 1 * * * /opt/batch/refund_journal.sh
```
② 고친 코드
```sh
30 1 * * * /opt/batch/with_lock.sh refund_journal /opt/batch/refund_journal.sh
# with_lock.sh: DB advisory lock 획득 실패 시 "skipped: locked" 기록 후 종료 0
```
무엇이 깨졌나: active/standby 전제가 깨졌을 때 막아 줄 장치가 없었다 — 배치가 "한 노드에서만 돈다"는 가정에 기댔다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| 공통 잠금 래퍼 | 공유 DB 접근 | 작음 | 잠금 해제 누락 시 다음 회차 건너뜀 | 기본 |
| 회차 키 대사 | 대사 테이블 스키마 변경 | 중간 | 키 생성 규칙 불일치 | 병행 |
| 크론 단일 스케줄러로 이전 | 스케줄러 도입 | 큼 | 스케줄러 장애가 전체 배치 정지 | 장기 |

**결론**: 배치 이중 실행은 사내가 막는다 — 잠금 래퍼를 템플릿으로 강제하고 대사에 회차 키를 남긴다.
