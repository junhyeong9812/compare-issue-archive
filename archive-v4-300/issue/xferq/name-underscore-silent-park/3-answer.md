# issue/xferq/name-underscore-silent-park — 정답

태그: `silent-failure` · `contract-drift`

## 정답
<!-- 질문 1:1 대응 -->

1. **나오지 않는다.** `HBP_RECON_K01_20260814_R1.dat`에는 `_`가 4개 있다.\
`send`는 그래도 exit 0과 접수 번호를 출력하지만 전송은 st 6으로 저장되고, `ls`·`pull`은 st 2인 전송만 보여 준다.\
`status <접수번호>`는 `접수번호 상대 이름 바이트 st`를 탭으로 출력하는데, 이 파일은 마지막 칸이 `6`이다 — 상대 수신함에 들어간 파일은 `2`다.\
벤더 `--help`에는 이 동작이 없고 stderr도 비어 있어서, 호출부는 성공으로 받아들인다.
   > **묶임(st 6)** — 스풀에 저장은 됐지만 상대 수신함으로 넘어가지 않은 상태. 벤더 문서에 없는 동작이다.

2. **기준은 원격 이름의 `_` 문자 개수, 4개 이상이면 묶인다.** `A_B_C_D.dat`(3개)는 수신함에 들어가고 `A_B_C_D_E.dat`(4개)는 묶인다.\
`_` 없는 50자 넘는 이름은 들어간다 — 길이 기준이 아니다.\
`A__B__C.dat`처럼 빈 필드가 있어도 `_` 4개라 묶인다 — 필드 의미가 아니라 글자 수다. `-`와 `.`은 세지 않는다.\
이름에 허용되지 않는 문자(공백·한글 등)는 반대로 E16으로 시끄럽게 거부된다 — 묶임과는 다른 경로다.

3. **재전송 표시가 `_`를 하나 더 붙였다.** 대사 파일 이름은 `HBP_RECON_<카드사>_<YYYYMMDD>.dat`(`_` 3개)였고, 재전송 때만 `_R<n>`을 붙였다.\
첫 전송분은 `_` 3개라 늘 들어갔고, 재전송분은 4개라 전부 묶였다.\
배치는 접수 번호를 받으면 "재전송 완료"로 기록했으므로 로그·종료 코드가 모두 정상이었고, 카드사가 "정정분을 못 받았다"고 문의해서야 알았다.

4. **문제는 길이가 아니라 `_` 개수였다.** 1차 조치로 날짜를 6자리로 줄인 `HBP_RECON_K01_260814_R1.dat`처럼 이름을 줄였지만, `_`가 그대로 4개여서 재전송분은 계속 묶였다.\
이름의 합의 부분을 바꾸는 것 자체도 대처가 아니다 — 상대 적재기는 합의한 접두·날짜 형식으로 파일을 골라 가므로, 그 부분을 바꾸면 수신함에 들어가도 적재되지 않는다.\
올바른 교정은 합의 접두는 손대지 않고 덧붙이는 부분만 `-R1`처럼 다른 구분자로 붙이는 것이다.
   > **합의 접두** — 상대 시스템과 약속한 이름 앞부분. 상대가 파일을 골라 가는 열쇠라 우리 쪽 사정으로 바꿀 수 없다.

5. **묶인 전송은 그대로 남는다.** 같은 내용을 올바른 이름으로 다시 보내면 새 접수 번호의 전송이 생기고(st 2), 원래 묶인 건은 st 6으로 스풀에 남는다.\
그래서 "묶이면 다른 이름으로 다시 보내기"를 상시 대처로 두면 묶인 전송이 쌓이고, 접수 번호 추적도 둘로 갈린다.\
처음부터 규칙에 맞는 이름으로 보내고, 이미 묶인 건의 정리는 벤더 창구와 합의한다.

6. **접수 번호는 스풀이 받았다는 뜻일 뿐이다.** `xferq`는 상대 수신함에 넣었는지와 무관하게 접수 번호를 준다.\
배치는 보낸 뒤 접수 번호마다 `status`의 st가 2인지 보거나, `ls --to <상대>`에 보낸 이름이 모두 나오는지 대조해야 한다.\
더 근본적으로는 이름을 만들 때 `_` 규칙을 지켜 묶임 자체가 생기지 않게 한다 — 대조는 그 규칙이 깨졌을 때 알아채는 안전망이다.

## 문제 구조 (추상화 코드)

### 변형 A — 덧붙인 표시가 `_`를 늘려 조용히 묶임 (재전송 파일)
① 문제 코드
```java
String name = String.join("_", "HBP", "RECON", partner, ymd);   // '_' 3개
if (resend > 0) name += "_R" + resend;                           // '_' 4개 → st 6, 그래도 exit 0
String ticket = transfer.send(partner, file, name + ".dat");
job.markDelivered(ticket);                                       // "전달 완료"로 오인
```
② 고친 코드
```java
String name = String.join("_", "HBP", "RECON", partner, ymd);   // 합의 접두는 그대로
if (resend > 0) name += "-R" + resend;                           // 덧붙임은 '_' 아닌 구분자 → '_' 3개
String ticket = transfer.send(partner, file, name + ".dat");
```
무엇이 깨졌나: 전송 서비스는 이름의 `_` 개수로 묶음 여부를 정하는데, 호출부는 덧붙이는 표시를 `_`로 이어 붙였다 — 재전송분만 4개가 되어 묶였고, 접수 번호·exit 0 때문에 성공으로 기록됐다.

### 변형 B — 길이 문제로 오인해 이름을 줄인 1차 조치
① 문제 코드
```java
String name = String.join("_", "HBP", "RECON", partner, yymmdd(day)) + "_R" + resend;  // 짧아졌지만 '_' 4개 그대로 → 여전히 st 6
```
② 고친 코드
```java
String name = String.join("_", "HBP", "RECON", partner, ymd) + "-R" + resend;          // 합의 형식 유지 + '-' 덧붙임
```
무엇이 깨졌나: 원인을 이름 길이로 짐작해 합의한 날짜 형식까지 줄였다 — `_` 수가 그대로라 묶임은 계속됐고, 형식이 바뀐 이름은 들어가더라도 상대 적재기가 고르지 못한다.

### 변형 C — 접수 번호로 전달 완료를 판정함 (확인 누락)
① 문제 코드
```java
for (File f : batch) f.markDelivered(transfer.send(partner, f, nameOf(f)));   // 접수 = 전달이라고 가정
```
② 고친 코드
```java
for (File f : batch) f.setTicket(transfer.send(partner, f, nameOf(f)));
Set<String> inBox = transfer.ls(partner).names();                              // 상대 수신함으로 판정
for (File f : batch)
    if (!inBox.contains(nameOf(f))) alert("not delivered: " + nameOf(f) + " st=" + transfer.status(f.ticket()).st());
```
무엇이 깨졌나: 벤더가 성공 신호(접수 번호·exit 0)를 전달 여부와 무관하게 냈는데, 호출부가 그 신호를 상대 수신함 확인 대신 썼다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| 덧붙임을 `-` 등으로 붙여 `_` ≤ 3 유지 | 벤더 규칙(`_` 4개 이상 묶임)을 안다 | 작음 | 상대가 새 덧붙임 형식을 모르면 적재 규칙 확인 필요 | 모든 send 호출부 — 기본 |
| 묶이면 다른 이름으로 재전송 | `status` 확인 후 재시도 | 중간 | 묶인 전송이 스풀에 쌓임, 접수 번호가 둘로 갈림 | 선택하지 않은 방법 |
| 이름을 줄이거나 합의 형식을 바꿈 | 길이가 원인이라는 짐작 | 작음 | `_` 수가 같으면 묶임 그대로, 형식이 바뀌면 상대 적재기가 못 고름 | 선택하지 않은 방법 |
| 사후 `status`/`ls` 대조 + 알림 | 조회 권한 | 중간(호출 수 증가) | 묶임 자체는 막지 못함 | 이름 규칙과 함께 안전망으로 |

**결론**: 이름 규칙을 지키는 것이 근본 대처이고, `status`/`ls` 대조는 규칙이 바뀌거나 다른 경로에서 같은 일이 생길 때를 위한 안전망이다. 둘을 함께 둔다.
