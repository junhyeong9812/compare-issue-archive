# issue/smsgw/tps-429-retry-no-jitter — 정답

태그: `performance` · `retry-storm`

## 정답
<!-- 질문 1:1 대응 -->

1. **약 400건 중 100건 이상이 `429`다.** 그리고 1초 뒤 재시도분이 새 요청과 합쳐져 다음 초에도 한도를 넘는다 — 429 비율이 줄지 않고 유지된다.

2. **거부된 요청도 한도 창을 차지하기 때문이다.** 요청 총량만 늘고 성공 건은 줄었다. 실측 성공 처리량은 300 → 120 TPS로 떨어졌다.

3. **거의 0이지만 완전히는 아니다.** 게이트웨이의 1초 창과 우리 시계 창이 어긋나 경계에서 순간 초과가 날 수 있다 — 그래서 한도의 90%(270 TPS)로 잡고 재시도는 백오프로 둔다.

4. **게이트웨이 응답 코드 분포를 먼저 본다.** 429 비율이 높으면 우리 쪽 송신 속도 문제, 접수는 정상인데 DLR이 늦으면 통신사 쪽이다.

## 문제 구조 (추상화 코드)

### 변형 A — 고정 간격 재시도
① 문제 코드
```python
for msg in batch:
    while True:
        r = smsgw.send(msg)
        if r.status != 429: break
        time.sleep(1)                       # 모든 워커가 같은 박자로 재시도
```
② 고친 코드
```python
bucket = TokenBucket(rate=270)              # 계약 300 TPS의 90%, 워커 간 공유(Redis)
for msg in batch:
    for attempt in range(6):
        bucket.acquire()
        r = smsgw.send(msg)
        if r.status != 429: break
        time.sleep(min(30, 2 ** attempt) * random.uniform(0.5, 1.5))
```
무엇이 깨졌나: 상대 한도를 무시하고 송신 속도를 워커 수로 정했고, 재시도가 동기화돼 혼잡을 키웠다.

## 방안 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|---|
| 공유 토큰 버킷 | 워커 간 공유 저장소 | Redis 의존 | 저장소 장애 시 정지 | 기본 |
| 지수 백오프 + 지터만 | 없음 | 작음 | 초기 폭주는 그대로 | 소량 발송 |
| 계약 TPS 상향 | 비용 | 큼 | 다음 이벤트에서 재발 | 상시 물량 증가 시 |

**결론**: 송신 속도는 우리 쪽에서 한도 아래로 제어하고, 재시도는 지터를 넣어 흩는다.
