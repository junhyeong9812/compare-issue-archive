# issue/tokvault/hsm-session-cap-latency — 정답

태그: `performance` · `hsm`

## 정답
<!-- 질문 1:1 대응 -->

1. **세션이 모자라 요청이 대기했다.** 세션을 못 얻은 요청은 풀 대기열에서 최대 2초를 기다렸다.

2. **더 느려진다.** 세션 총량이 고정이다.

3. **세션 획득 대기 시간.** HSM 호출 처리 시간은 피크에도 15ms로 일정했다.

4. **6개다(64 ÷ 10, 내림).** 그래서 세션 풀 크기를 고정값이 아니라 기동 시 `한도 ÷ 최대 파드 수`로 계산하게 바꿨다.

## 문제 구조 (추상화 코드)

① 문제 코드
```yaml
hsm: { sessionPool: 16 }      # 파드 6개 → 96
```
② 고친 코드
```yaml
hsm: { sessionPool: 10 }      # 64 / 6 = 10, 여유 4
```
무엇이 깨졌나: 공유 자원 한도를 파드 수와 함께 계산하지 않았다.

## 방안 비교

| 방안 | 비용 | 실패 모드 | 맞는 조건 |
|---|---|---|---|
| 세션 풀 재산정 | 작음 | 파드 증설 시 재계산 | 기본 |
| HSM 증설 | 큰 비용 | 없음 | 장기 |

**결론**: 공유 한도는 전체 인스턴스 합으로 나눠 쓴다.
